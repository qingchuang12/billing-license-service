# plan-2.1：许可证激活与兑换码激活的重叠治理

## 结论先行
**是重叠，但不只是"重复代码"这么简单。** 真正的不合理有四点：

1. **凭证通道增殖**：现在连同已规划的一共**四条**路径都能拿到"绑定设备 + 签名令牌"，
   客户端要认四种入口。
2. **绑定/签发/幂等逻辑被复制**：兑换侧已有成熟的 B9 幂等与 IP 风控，若激活端点另写一套，
   两套策略必然漂移，最终出现"一边幂等、一边重复签发"的资损级不一致。
3. **安全自相矛盾（最严重）**：账号页**明文展示 licenseKey**，而计划中的激活规则是
   "未绑定即可绑定"——两条叠起来等于**谁先抢到算谁的**，明文展示的 key 会被抢绑。
4. **兑换码本质是补丁产物**：它是"购买时本地没有客户端"的权宜之物；一旦有了账号 + 在线激活，
   在线场景下它就可以退役。

---

## 一、四条现有/计划路径（已核实）

| # | 路径 | 入口 | 触发条件 | 证据 |
|---|---|---|---|---|
| 1 | **购买直签发** | `CheckoutRequest.machineId` → 支付成功后签发即绑定 | 购买时带机器码 | `CheckoutRequest.java:34-37` |
| 2 | **兑换码** | `POST /api/redeem/redeem`（公开） | 购买时**没带**机器码 → 发码 → 客户端兑入 | `RedeemCodeController.java:48`；`RedeemCodeRequest.java:29-32` |
| 3 | **在线校验** | `GET /api/licenses/verify/{licenseKey}` | 已绑定后取回 signedToken | `LicenseController.java:47`；`LicenseService.mapToResponse` 行384 回写签名令牌 |
| 4 | **在线激活（待开发）** | `POST /api/licenses/activate` | 持 licenseKey 绑定设备 | 本文件 A2（尚未落地） |

兑换侧还有几个**值得沿用的成熟能力**，新端点不该重写而应复用：
- **B9 幂等**：同一兑换人重试同一枚已用码 → 直接返回其已签发的 License
  （`RedeemCodeService.java:187-196`，注释写明是为了修"钱已付、码已耗、License 拿不到"的资损）
- **IP 风控**：`checkRedeemIp` + `recordRedeemFailure` 失败计数（`RedeemCodeService.java:159-175`）

## 二、改造方案

### 方案 A（推荐）：合并为单一「凭证激活」端点 + 单一内核
```
POST /api/licenses/activate  { credential, machineId, customerEmail? }
```
服务端**自动识别凭证类型**（兑换码 `RC-xxxx` / 许可证密钥 `XXXX-XXXX-XXXX-XXXX`），
内部各走各的校验，但**统一返回** `{ signedToken, licenseKey, status, machineId }`。
客户端从此只认一个入口。

配套：
- 抽出 **`CredentialBindingService`** 作为"绑定/签发"的**唯一内核**，被购买直签、兑换、激活三者复用，
  幂等与签名只此一份。
- 幂等口径沿用 B9（同一主体重试返回既有 License，不二次签发）。
- 频控口径沿用兑换侧 `checkRedeemIp`。**注意**：合并通道后要按最短板取值——
  兑换码（`RC-xxxx`，熵远低于许可证密钥）更易被暴力猜测，因此阈值必须以兑换码为准取严档。

### 方案 B：保留两个端点，仅抽公共内核
对外不改（`/api/redeem/redeem` 与 `/api/licenses/activate` 并存），内部统一到同一内核。
风险低，但客户端仍要认两个入口，没解决入口增殖。

### 归属校验（安全红线，必须落实）
无论哪个方案，**绑定都必须先过归属判定**，不能"谁拿着串谁就能绑"：
- 兑换码路径：沿用现有语义（持码即视为持有人，配合频率限制）；
- 许可证密钥路径：**必须要求调用者就是该 License 的持有人**——
  推荐走"登录后激活"（复用 `GET /api/account/licenses` 取本人持证），
  因为账号页明文展示了 key，"仅凭 key 即可绑定"会在多人可见的场景下被抢绑。
