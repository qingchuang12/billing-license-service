## 三、实现思路（触点 → 步骤 → 取舍 → 风险回滚）

### T1（上线门禁 · 高）全渠道真实沙箱/生产联调

- **触点**：各 `PaymentStrategy`（`src/main/java/.../payment/impl/`）+ `WebhookController` + `ChannelConfigValidator`（生产缺失密钥 fail-fast）。
- **前置阻塞（需用户提供）**：① 各渠道沙箱/测试密钥（Stripe test key 最易获取，建议优先打通端到端）；② 公网可达的 Webhook 回调端点（Hookdeck / ngrok 隧道或测试环境部署）；③ 沙箱后台配置 Webhook 目标 URL 与签名密钥。
- **步骤**：逐渠道按 [`archive/plan-t1-channel-verify.md` §2.3](./archive/plan-t1-channel-verify.md) 的 5 步联调清单执行；Paddle 重点核金额出库为最小货币单位整数串（`"999"` 而非 `"9.99"`，H7 已修）。
- **取舍**：5 渠道代码层已审计通过，联调只验「配置 + 网络 + 真实约定」，不改代码；首跑打印 `headers` key 集合做一次大小写稳健性确认（非缺陷）。
- **风险回滚**：联调期间渠道以 `billing.channel.*.enabled=false` 关停（渠道配置自检 missingConfig 为唯一事实源）；验签异常先反向用错误密钥/篡改 payload 复核是配置错还是代码错。

### T2（中）性能压测

- **触点**：`CheckoutService.getStatus` 补偿查询、`RateLimitService`（R3 轮询冷却/过期淘汰）、并发兑换/发放路径。
- **步骤**：起真实 PG + 配齐单渠道测试密钥 → 用压测工具（如 JMeter/wrk，工具选型届时定）打 getStatus 补偿与并发兑换 → 记录 P95/P99、限流淘汰行为、连接池占用。
- **取舍**：只压当前单实例形态；Redis 共享限流等多实例场景不在本版。
- **风险回滚**：压测在独立环境执行，不触生产数据。

### T3（安全 · 高）客户端 exe 验签逻辑

- **范围**：exe 客户端侧 JWS 验签模块（不在本仓库，需客户端仓库配合）。
- **关注点**：算法降级风险（w13：禁 ES384/RS512 等弱算法，仅允许服务端实际签名算法）、机器码绑定校验、过期/吊销 License 的离线行为、公钥硬编码不可替换。
- **步骤**：服务端用真实私钥签发正常/篡改/过期/吊销/换机器码 5 类样本 → 客户端逐一验证接受/拒绝行为。

### T4（中）渗透测试

- **范围**：Webhook 验签、管理端双 Key 鉴权、限流、CORS、异常脱敏、Actuator 暴露面。
- **步骤**：部署测试环境 → 外部渗透（可用自动化工具初扫 + 人工复验）→ 发现项按严重度回流本 plan TODOS 修复。
- **取舍**：依赖 T1 的测试环境部署，建议排在 T1 之后。

## 四、依赖与顺序

T1（先 Stripe 后全渠道）→ T2 / T3 可并行 → T4 最后（复用 T1 测试环境）。任一闸门发现问题 → 回流 TODOS 修复并复验，不绿灯不进下一项。
