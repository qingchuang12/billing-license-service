## 一、密钥类（License 的唯一信任根）

> 私钥一旦泄露，任何人都能伪造 License，且客户端离线验签无法察觉。本节优先级最高。

### 1.1 形态要求（代码事实，先懂再生成）

`LocalKmsService.buildKeyPair()` 只接受两种形态（`src/main/java/com/billing/license/infrastructure/kms/LocalKmsService.java:86-105`）：

| 形态 | 条件 | 处理 |
|---|---|---|
| **裸 32 字节 Ed25519** | 私钥或公钥文件长度 = 32 字节 | 手工补 DER 前缀（PKCS#8 / SPKI），算法判定为 `Ed25519` |
| **DER 字节** | 非 32 字节 | 按 PKCS#8（私钥）/ X.509（公钥）解析，算法自动识别 EC→RSA |

- ❌ **PEM 文本不被支持**（`-----BEGIN …` 解析失败）；EC/RSA 也必须用 `-outform DER` 导出 DER。
- ❌ 判断是「私钥**或**公钥任一为 32 字节即走 Ed25519 分支」→ **切勿混用**（如 32B 私钥配 DER 公钥）。
- ⚠️ **密钥懒加载**：首次 `sign`/`verify` 才读盘（`LocalKmsService.java:66-84`）→ **密钥缺失不会导致启动失败，只会在第一笔签发时炸**。部署后必须做一次真实签发冒烟（[§7-A](#a-授权链路端到端)），别把「健康检查通过」当成「能签发」。

路径优先级：环境变量 `PRIVATE_KEY_PATH` / `PUBLIC_KEY_PATH` → `billing.private-key-path` / `billing.public-key-path`（默认 `/keys/*.key`）（`LocalKmsService.java:52-63`）。

### 1.2 生成密钥对（**全局唯一权威命令源**，其余文档一律引用本节）

> 实测（2026-09-18，OpenSSL 3.2.4 / JDK 25）：旧文档的 `openssl pkey … -rawin` 直接报 `Unknown option or cipher: rawin`；
> `genpkey`/`genrsa` 产出 **PEM**，与 §1.1 的加载器不兼容；对现有裸私钥执行 `openssl pkey -in keys/private.key -pubout` 会报 `Could not find private key`。
> 下列命令（含两条自检）**已在本机实跑通过**。

```bash
# 1) 生成 Ed25519 密钥（PEM，仅作中间产物）
openssl genpkey -algorithm ed25519 -out /tmp/private.pem

# 2) 导出「裸 32 字节」私钥与公钥（DER 结构的末 32 字节即裸密钥）
openssl pkey -in /tmp/private.pem -outform DER        | tail -c 32 > keys/private.key
openssl pkey -in /tmp/private.pem -pubout -outform DER | tail -c 32 > keys/public.key

# 3) 立即销毁中间产物（PEM 是完整私钥，不能留在机器上）
shred -u /tmp/private.pem 2>/dev/null || rm -f /tmp/private.pem
```

**自检（必做，两条均已实测通过）**

```bash
# 3.1 体积必须都是 32 字节
wc -c keys/private.key keys/public.key          # 期望：32 与 32

# 3.2 签名/验签回环：证明这对裸密钥正是服务端加载器所认的格式，且两两配对
(printf '\x30\x2e\x02\x01\x00\x30\x05\x06\x03\x2b\x65\x70\x04\x22\x04\x20'; cat keys/private.key) > /tmp/p.der
(printf '\x30\x2a\x30\x05\x06\x03\x2b\x65\x70\x03\x21\x00'; cat keys/public.key)  > /tmp/q.der
printf 'smoke' > /tmp/m.txt
openssl pkeyutl -sign   -rawin       -inkey /tmp/p.der -keyform DER -in /tmp/m.txt -out /tmp/s.bin
openssl pkeyutl -verify -rawin -pubin -inkey /tmp/q.der -keyform DER -in /tmp/m.txt -sigfile /tmp/s.bin
# 期望：Signature Verified Successfully（签名长度 64 字节）
rm -f /tmp/p.der /tmp/q.der /tmp/m.txt /tmp/s.bin
```

> 前缀常量（与外置工具对齐用）：私钥 PKCS#8 前缀 `302e020100300506032b657004220420`（16B，`LocalKmsService.java:110-112`）；公钥 SPKI 前缀 `302a300506032b6570032100`（12B，`:118-120`），与客户端 `ai-tools/src/main/license/keys.ts:27` 完全一致。

### 1.3 放置与注入（含 `keys/` 目录用途 ← 合并自原 `keys/README.md`）

`keys/` 目录用途：本地 KMS（`KMS_PROVIDER=local`）签发/验签用的 Ed25519 密钥对存放处，由 `docker-compose.yml` 只读挂载进容器 `./keys:/keys:ro`（`docker-compose.yml:20`），容器内路径即默认值 `/keys/*.key`。

| 文件 | 说明 |
|---|---|
| `private.key` | 签名私钥，**绝不外传、绝不入库** |
| `public.key` | 验签公钥（客户端内置用于离线验签，可分发） |

| 场景 | 做法 |
|---|---|
| 本地 / compose | 按 §1.2 生成后放 `keys/private.key`、`keys/public.key`；compose 已只读挂载，**无需额外配置** |
| 本地显式指定 | `PRIVATE_KEY_PATH=./keys/private.key`、`PUBLIC_KEY_PATH=./keys/public.key`（见 `.env.example`） |
| 生产（推荐） | 用 Secret / 挂载卷注入，或直接给 `PRIVATE_KEY_PATH` / `PUBLIC_KEY_PATH` 绝对路径；**生产不使用 `keys/` 目录** |

- ⚠️ **`keys/` 不入库**：`.gitignore:44` 已忽略 `keys/` 与 `*.key`（故原 `keys/README.md` 也无法共享，其内容已并入本文档）。镜像侧 `.dockerignore` 亦已排除 `keys/*`。
- ⚠️ 生产机私钥权限 `600`、属主为运行用户（容器内为非 root `appuser`，`Dockerfile:17-20`）；**密钥不得进镜像、不得进 Git、不得进日志**。

### 1.4 轮换（kid）与「旧证仍可验」

签发时 JWS header 的 `kid` 取自 `billing.license-kid`（默认 `license-key-1`，`LicenseIssuer.java:37-38,49`）；验签按 kid 选公钥，未知 kid 回退主公钥并告警（`LocalKmsService.java:130-158`）。

**顺序（不可颠倒）**：服务端保留双公钥 → 客户端发版内置新公钥 → 切换签发 kid。

1. 按 [§1.2](#12-生成密钥对全局唯一权威命令源其余文档一律引用本节) 生成新密钥对 → 覆盖 `keys/private.key`/`public.key`（旧**公钥**另行留存）；
2. 设 `BILLING_LICENSE_KID=license-key-2`；旧 kid 公钥经 `billing.public-keys.<kid>` 或 `PUBLIC_KEY_<KID>`（`-`→`_`、大写）注入，**旧证才仍能验签**；
3. **客户端必须先发版内置新公钥**，否则老客户端验不了新证。

> 完整脚本与回滚窗口见 `scripts/README.md`「License 签名密钥轮换流程」。
> ⚠️ 边界：只做「按 kid 选公钥」，**不做**多版本并存签名与自动轮换调度（边界见 `docs/plan-7.0.md` 的「范围与边界」）；已签发 token 不会重签，历史 kid 公钥须长期保留。

### 1.5 当前密钥的性质与上线处置

**结论：当前 `keys/` 下是「调试密钥」，不作为生产密钥使用 → 不轮换、不清理 git 历史（N1/N2 按用户 2026-09-18 决策关闭）。**

- **为什么不用做**：该私钥曾随提交进入 `origin/main` 历史，但**从未用于签发真实售卖的 License**（上线前无真实客户数据）→ 泄露面 = 无实际损失。
- **但不是"忽略"**：上线当天按 §1.2 生成生产密钥对 + 替换客户端公钥（§1.6），调试密钥自此作废 —— 见 [§10-1](#10-1-生成生产签名密钥并同步客户端)。
- ⚠️ 配套两点：① 上线前**不要用调试密钥签发任何"要长期有效"的 License**（如预发客户的买断证），那会变成真实损失；② 客户端内置正是这把调试公钥（§1.6 实测同值）→ 换生产密钥**必然包含客户端重新打包发版**。
- 将来仓库若转公开、确需清理历史：按 `git filter-repo` + force push 单独安排（高风险，需协调协作方）。

### 1.6 客户端侧配套（换生产密钥时必须同步改）

| 位置 | 内容 | 动作 |
|---|---|---|
| `ai-tools/src/public.key` | 32 字节裸公钥，实测 = 当前调试密钥的 `keys/public.key`（`73a23b…7437`） | 换生产密钥时替换为新公钥 |
| `ai-tools/src/main/license/keys.ts:35` | 编译期硬编码兜底公钥（同一值） | 同步替换 |
| `ai-tools/package.json:105-108` | `extraResources` 把 `src/public.key` 落到 `resources/license/public.key` | 无需改（随源文件） |

> 客户端公钥查找顺序：包外 `license/keys/<kid>.key` → 包外 `license/public.key` → asar 内同名 → 硬编码兜底（`ai-tools/src/main/license/keys.ts:107-142`）。**替换公钥无需重装/改版本**（改包外文件即可），但改客户端默认公钥意味着要重新打包分发。
> ⚠️ 客户端默认 `kid='default'`、服务端签发 `kid='license-key-1'`：当前靠 `public.key` 兜底可用；**启用多 kid 时两侧命名必须对齐**，否则老证（旧 kid）在新客户端会落入「未知 kid → 回退主公钥 → 验签失败」。

### 2.3 回调地址注册（渠道后台 ↔ 服务端必须一致）

回调入口固定 **5 个**（`controller/webhook/WebhookController.java`）：`POST /api/webhooks/{alipay, wechat, stripe, paddle, paypal}`。

每渠道三件事：

1. 渠道后台把 **Notify/Webhook URL** 填为 `${APP_BASE_URL}/api/webhooks/<渠道>`；
2. 把渠道后台的**签名密钥/公钥**填回服务端配置并重启；
3. **触发一次真实回调**：验签通过 → 订单转 `PAID` → 自动签发或生成兑换码。

- ⚠️ 反代/网关必须**原样透传回调原始报文**（验签基于原始 body，任何改写都会验签失败）；TLS 必须是受信任证书（渠道不回调自签证书地址）。

### 2.4 渠道自检与停用

### 3.3 初始管理员 bootstrap（仅首次部署）

> 代码：`AdminBootstrapService.java:52-94`、`AccountProperties.java:122-132`、`application.yml:260-271`。
> 这一节解释启动日志里那条 WARN：「库中不存在任何管理员，且未配置 `account.bootstrap-admin`」。

- **它解决什么问题**：全新库里一个账号都没有，而管理端 `/api/admin/**` 一律要求 `ROLE_ADMIN`（管理端鉴权 = 管理员 JWT，§5），结果是**没有任何账号能登录管理端**。以前只能由运维直连数据库手工造出第一个管理员（`scripts/db/promote-to-admin.sql`）；配上下面两个环境变量后，首次启动即自动建出来，免改库。

| 变量 | 对应配置项 | 用途 |
|---|---|---|
| `ACCOUNT_BOOTSTRAP_ADMIN_EMAIL` | `account.bootstrap-admin.email` | 初始管理员邮箱（入库前转小写） |
| `ACCOUNT_BOOTSTRAP_ADMIN_PASSWORD` | `account.bootstrap-admin.password` | 初始管理员**明文**口令，仅 bootstrap 这一次使用，入库前经 BCrypt 散列 |

> `account.bootstrap-admin` 是这两项的 YAML 父节点（命名空间），**不是第三个开关**。

- **生效条件＝库里没有任何 ADMIN（这是本设计的关键）**：逻辑挂在 `ApplicationReadyEvent` 上，先查 `countByRole(ADMIN)`。
  - 已存在任意管理员（无论是不是本配置建的）→ **整段配置完全失效**，连日志都不打。刻意「自废武功」：允许运维把这两行长期留在 `.env` 里忘了删，也不会在某次「管理员账号被误删」之后被人拿来重造一个后门账号。
  - 因此**它只在首次部署有意义**，稳态下每次重启都会静默走到「已失效」分支，无需再维护。
- **四种配置组合的行为**（`AdminBootstrapService.java:55-71`）：

| 情形 | 行为 |
|---|---|
| 已有任意 ADMIN | 静默跳过，配置完全失效 |
| 两项**都没配** | 只 **WARN** 并跳过，**不影响启动**（本文开头那条日志即此分支） |
| 只配了其中**一项** | 抛 `IllegalStateException` **拒绝启动**——"必须成对配置"，不留"配了但没生效"的糊涂账 |
| 两项都配 | 先过口令强度策略，再建号 / 提权（见下条） |

- **口令强度**：与注册 / 改密共用 `PasswordPolicy`（`PasswordPolicy.java:31-40`）→ 长度 **8–72** 且**必须同时含字母与数字**（受 `account.password-min-length` / `password-require-alnum` 约束）。不合规**直接拒启**，不是建号失败。上限 72 是 BCrypt 静默截断所致，故显式拒绝而非截断。
- **邮箱已注册时只提权、绝不改密码**（`AdminBootstrapService.java:76-83`）：该邮箱若早已注册为普通账号，只把 `role` 改成 ADMIN，**配置里的明文口令不会写进去**——否则会顶掉用户正在使用的密码。账号 `status=ACTIVE`、`emailVerified=true`（不占用注册链路）。
- **上线怎么做**：
  1. 首次部署：在 `.env` 里成对填上两行（口令自行设定，注意上面强度要求），启动一次即建出管理员；
  2. 建好之后：可以不管它（已被"有 ADMIN"短路），**也可注释掉这两行**——更干净，也能防止日后误判"这配置还在生效"；
  3. 口令进 `.env` 即属敏感值，遵守 §10-2 的口径：**不得复用曾在仓库或本文档出现过的值**。
  4. 日志会提示「请于首次登录后立即修改密码」→ 登录管理端后改密，并按 §5 建议**开启二次因子**（B8）。
- **不用 bootstrap 的兜底路径**：照旧 `scripts/db/promote-to-admin.sql` 手工提权（先注册普通账号再跑 SQL，**非 Flyway、需手动执行**）。两条路径产物相同（一个 `role=ADMIN` 的账号），任选其一。
- **判据**：首次启动日志出现 `bootstrap：已创建初始管理员 <邮箱>`（或提权为管理员）；随后 `POST /api/account/login` 用该邮箱口令可拿到 `accessToken`，带它调 `GET /api/admin/payment-channels` 返回 200 而非 401。

> 单测已覆盖上述全部分支：`src/test/java/com/billing/license/service/AdminBootstrapServiceTest.java`（已有管理员时整体失效 / 未配置只 WARN 不写库 / 空库建号且口令为散列 / 已有邮箱只提权不改密 / 半配置拒启 / 弱口令被共用策略拒绝）。

### 6.5 域名 / TLS / 反代

- `api.ywhome.top`（客户端兑换地址）解析到反代并终结 TLS；反代需：原样转发回调 body（§2.3）、注入 `X-Forwarded-For` 且与 `BILLING_TRUST_XFF` 一致、超时 ≥ 15s（客户端 `redeemTimeoutMs=15000`）。
- 前端（收银台页面）与 API 不同源 → 配 `APP_CORS_ALLOWED_ORIGINS`；**但收银台落地页已后端内嵌（与 `/api` 同源 `/checkout/`）**，该页面本身无需 CORS，仅当后续引入独立前端域名时才需配置。

### 6.6 回滚预案（上线前必须写好）

1. **应用**：保留上一版本镜像 tag，回滚 = 换 tag 重启（V1–V11 均加列/建表，回退应用版本不破坏数据）；
2. **配置**：环境变量变更留档（渠道开关可即时止血）；
3. **数据**：`pg_dump` 备份 + 恢复演练；
4. **支付**：异常时把渠道移出 `PAYMENT_ENABLED_CHANNELS` 重启，避免持续收款不发货。
