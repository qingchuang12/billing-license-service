## 三、Critical 问题（12 项：主流程必然故障 / 直接资损 / 风控失效）

### C1. PayPal Webhook 解析基于不存在的报文结构 → PayPal 付款后永不发货

- **位置**：`service/payment/impl/PayPalStrategy.java` L213-226
- **问题**：`PAYMENT.CAPTURE.COMPLETED` 的 `resource` 是 capture 对象（真实结构：`id`/`amount`/`supplementary_data.related_ids.order_id`/`status`），**没有 `reference_id`、没有 `purchase_units`**（已对照 PayPal 官方样例核实）。且 `createPayment`（L84-87）未设置 `custom_id`，无处携带订单号。
- **后果链**：`orderId = null` → 订单查不到、金额校验被跳过 → `paymentId = capture ID` 与落库的 PayPal 订单 ID 不匹配 → `updatePaymentStatus` 抛"支付记录不存在" → 500 回滚 → PayPal 重试 25 次/3 天全部失败 → **用户已付款、无 License、无兑换码**。
- **测试假信心**：`PayPalStrategyTest` L95-112 的 payload 是凭空构造的（resource 里塞了不存在的 `reference_id`/`purchase_units`）。
- **修复**：下单时在 `purchase_units[].custom_id` 写入 orderNo，回调读 `resource.custom_id`（或 `supplementary_data.related_ids.order_id`）；`paymentId` 取关联订单 ID；按官方真实样例重写测试。

### C2. Paddle 创建交易请求体用 camelCase，API 实为 snake_case → Paddle 渠道完全不可用

- **位置**：`service/payment/impl/PaddleStrategy.java` L132-148
- **问题**：`unitPrice`/`currencyCode`/`customData` 应为 `unit_price`/`currency_code`/`custom_data`（Paddle Billing v2 官方文档核实）；ad-hoc price 还要求 `tax_mode` 与 `product` 字段。
- **后果**：请求被 422 拒绝 → `createPayment` 恒走 FAILED → `selectProvider` 抛 `PAYMENT_CREATE_FAILED` → **Paddle 渠道 100% 不可用**。
- **修复**：改正字段名并补必填字段；`PaddleStrategyTest.createPayment` 断言同步修正（当前测试锁定了错误键名）。

### C3. Paddle Webhook 解析同样 camelCase → orderId 恒为 null → 回调 500 死循环

- **位置**：`service/payment/impl/PaddleStrategy.java` L265-267、L278-280、L290
- **问题**：`customData`/`currencyCode`/`current_period` 应为 `custom_data`/`currency_code`/`current_billing_period`（同文件其余字段已是 snake_case，四处系笔误残留）。
- **后果**：真实 `transaction.completed` 回调解析出 `orderId=null` → `fulfillOrder(null)` 抛异常 → 500 回滚 → Paddle 持续重试永失败 → **Paddle 付款永不发货**；订阅周期字段读不到 → 续期推算失效。
- **修复**：三处键名改正；用官方 webhook 样例补测试。

### C4. 微信查单 URL 多拼 `/query` 后缀且签名串缺 query 参数 → 微信对账补偿完全失效

- **位置**：`service/payment/impl/WechatPayStrategy.java` L63-64、L249-253
- **问题**：正确接口为 `GET /v3/pay/transactions/out-trade-no/{out_trade_no}?mchid={mchid}`（**无 `/query` 后缀**，官方文档核实）；且官方签名规范要求签名串**含查询参数**，代码签的是无 query 的路径。
- **后果**：查单恒 404/401 → `compensateFromChannel` 永不确认成功 → 微信 Webhook 丢失时无任何兜底（叠加 C5，微信链路补偿瘫痪）。
- **修复**：URL 与签名串均改为 `.../out-trade-no/{outTradeNo}?mchid={mchId}`。

### C5. 轮询补偿只改 CheckoutSession、不改 Order、不发货 → 死循环异常或"未支付已发货 + 重复发码"资损

- **位置**：`service/CheckoutService.java` L306-323（compensateFromChannel）、L255-283（getStatus 发放分支）
- **问题**：补偿确认渠道 SUCCESS 后仅 `session.setStatus(PAID)`，**既不 `order.markPaid()` 也不复用发货逻辑**，与 L233 注释"复用 fulfillOrder 等价逻辑"不符。
- **后果**（Webhook 丢失场景，正是补偿的设计目标）：
  - 有 machineId 订单：轮询进入 `issueLicensesForOrder` → LicenseService L98-101 校验 `paymentStatus != PAID` 抛异常 → **整个事务回滚（含 session=PAID 与冷却时间戳）** → 客户端轮询持续报错、冷却机制失效 → 用户付了钱永远拿不到 License；
  - 无 machineId 订单：`generateCode` 无支付态校验直接发码，Order 恒 PENDING；Webhook 迟到到达时 `canFulfill()` 对 PENDING 返回 true → `markPaid` + **再次 generateCode → 一笔付款发两个兑换码 = 直接资损**。
- **修复**：补偿确认 SUCCESS 后复用与 `fulfillOrder` 等价的统一发货入口（Order/Session/幂等事件/发货同事务）；`generateCode` 按 orderId 幂等（已存在则返回已有码）。

### C6. 双币种回退逻辑金额与币种错配 → 静默资损（99 元买 99 美元商品）

- **位置**：`entity/Product.java` L111-126
- **问题**：`getPriceForRegion(true)` 当 `priceCny` 为 NULL 时回退取 `priceUsd` 数额，而 `getCurrencyForRegion(true)` **恒返回 "CNY"**——金额取对侧、币种按区域。
- **后果**：某产品漏配 `price_cny`（列可空、无管理端校验、手工 SQL 新增产品即触发）：国内订单 99.00 CNY 买 99 USD 商品（**少收约 87%**）；反向则多收 7 倍。无任何告警。
- **修复**：删除跨币种回退，目标档位缺失抛 `PRICE_NOT_CONFIGURED` 拒绝下单；币种与价格同源判定。

### C7. 全工程无 @EnableAsync → 5 处 @Async 全部失效，SMTP 故障回滚退款/发货事务

- **位置**：`BillingLicenseApplication.java`（仅 @EnableScheduling）；`service/notification/EmailNotificationService.java` L44/75/106/137/168（@Async）+ L67 等 5 处 `catch (MessagingException)`
- **问题**（已逐一验证）：① 无 @EnableAsync，@Async 不生效，邮件**同步**执行于事务内；② SMTP 连接失败抛 `MailSendException`（RuntimeException），**不被 `catch (MessagingException)` 捕获**。
- **后果**：
  - 退款路径（AdminService L149-157）：渠道钱已退 → 邮件异常 → **整个事务回滚 → 订单仍 PAID、License 仍 ACTIVE（退款 + 授权双得）**；重试退款被渠道拒绝 → 永久无法闭环；
  - 发货路径（WebhookController.fulfillOrder L323-341）：**付款不发货**，渠道重试撞同一故障。
- **修复**：① 启动类加 @EnableAsync；② catch 改为 `catch (Exception)`；③ 根治：邮件移出事务（afterCommit / 事件监听）。

### C8. 渠道退款失败时 REFUND_FAILED 状态因事务回滚永不落库

- **位置**：`service/AdminService.java` L129-136
- **问题**：`markRefundFailed` 落库后抛 `BusinessException`（RuntimeException）→ 默认回滚 → **失败状态一并回滚**。测试 `AdminServiceRefundTest` 是纯 Mockito 单测（无事务），断言与生产行为背离。
- **后果**：渠道退款失败时 DB 恒保持 PAID、无失败痕迹（仅 audit 日志），运营看不到待处理清单。
- **修复**：失败标记放独立事务（REQUIRES_NEW / TransactionTemplate）先提交再抛异常。

### C9. 限流环形缓冲 int 溢出 → 兑换码暴力猜测锁定永不触发（默认配置下风控静默失效）

- **位置**：`service/risk/RateLimitService.java` L75 + L139；默认值 `config/BillingProperties.java` L66
- **问题**（已验证）：`new TimestampRing(Integer.MAX_VALUE)` → 构造器 `Math.max(8, capacity + 1)` 中 `Integer.MAX_VALUE + 1` 溢出为 `Integer.MIN_VALUE` → 容量被钳制为 **8** → `record()` 计数上限 8；而 `recordRedeemFailure` 判断 `count > redeemFailureMax`（默认 **10**）→ **恒 false，REDEEM_BRUTE_FORCE 锁定永不触发**。
- **掩盖原因**：测试设 `redeemFailureMax=3`（3 < 8）恰好通过。
- **修复**：`(long) capacity + 1` 防溢出或传有限容量；补 `redeemFailureMax > 8` 回归测试。

### C10. 兑换限流 clientIp 可由请求体伪造 → IP 频控完全绕过

- **位置**：`dto/RedeemCodeRequest.java` L28（可反序列化字段）、`controller/RedeemCodeController.java` L83-86、`service/RedeemCodeService.java` L126-145
- **问题**（已验证）：Controller 仅当 `request.getClientIp() == null` 时才用服务端解析的 IP——**客户端 body 传了就用客户端的**。服务端精心实现的 H8 防伪造 `parseClientIp` 被架空。
- **后果**：公开端点 `/api/v1/redeem/redeem` 攻击者每次换随机 `clientIp` → `REDEEM_IP_LIMIT` 与 `REDEEM_BRUTE_FORCE` 全部失效（叠加 C9，暴力枚举兑换码无任何阻拦）。
- **修复**：`clientIp` 字段加 @JsonIgnore 或删除；Controller 无条件用服务端解析值覆盖。

### C11. LocalKmsService Ed25519 分支必然失败 → 默认推荐签名算法不可用，首次签发 100% 抛异常

- **位置**：`infrastructure/kms/LocalKmsService.java` L66-70、L91-105；默认配置 `application.yml` L43 `signature-algorithm: ED25519`
- **问题**（已验证）：① 密钥文件为 32 字节 raw → 走 Ed25519 分支 → `PKCS8EncodedKeySpec` 严格要求 DER 结构 → 必抛 `InvalidKeySpecException`；② 密钥为标准 DER（Ed25519 PKCS8 私钥 48 字节）→ 走 `detectAlgorithm` → EC/RSA KeyFactory 均无法解析 → `IllegalStateException`。**两条路都死**。
- **后果**：按默认配置文档生成 Ed25519 密钥挂载后，应用可启动（延迟加载 H12）但**首次签发 License（兑换/订单发货）100% 失败**。
- **修复**：raw 32 字节手工包装 PKCS#8 DER 前缀，或要求 DER 格式并启动期明确校验报错。

### C12. ChannelConfigValidator 强制 5 渠道凭证全配齐 → docker-compose 部署必然启动失败

- **位置**：`config/ChannelConfigValidator.java` L55-77；`docker-compose.yml` L7-16；`.env.example`
- **问题**：校验器**无条件**要求全部 5 渠道 13 项凭证齐全（application.yml 默认全空），而 `PaymentServiceFactory` 的 `enabled-channels` 设计明确支持子集启用/自动判定——**两者语义互斥**。docker-compose 环境变量无任何 `payment.*`，`.env.example` 也只模板化 4 项。
- **后果**：`docker compose up` 即抛 IllegalStateException 崩溃；只想启用支付宝+微信的合法部署无法启动；工厂的自动判定逻辑成为死代码。校验清单还与各策略 `missingConfig()`（声明的唯一事实源）不一致。
- **修复**：校验器仅对 `enabled-channels` 显式列出的渠道 fail-fast，或删除校验器（工厂 `logChannelReport` + `/api/admin/payment-channels` 已覆盖自检）。

## 五、Info 问题（30 余项，摘要）

**支付**：PaymentEvent.amount/currency 审计列从未赋值；reserveEvent 的 DataIntegrityViolationException 捕获因 flush 时机基本不触发（应 saveAndFlush）；退款后 Payment.status 停留 SUCCESS；支付宝未校验 app_id/seller_id 一致性；`Order.canFulfill()` 对 COMPLETED 返回 true；Stripe.apiKey 静态字段；微信大额（>¥21,474,836.47）intValue 溢出。

**订单**：状态机空转（CONFIRMED/PROCESSING/COMPLETED/CANCELLED 无流转代码，`setStatus` 仍 public 可绕过收敛出口）；locale 优先于 currency 判定区域（currency=USD+locale=zh-CN 判为国内）；selectProvider 不校验渠道与订单币种匹配（CNY 订单可选 Stripe）；两条签发路径逻辑不一致（webhook 用 issueLicense 仅签首个 item，轮询用 issueLicensesForOrder 按 quantity 全签）；V6 回填汇率硬编码 7.2（上线需核对）；订阅升降级无处理（建议文档化）。

**License**：redeem 失败时 EXPIRED 标记因 w5 异常回滚丢失；generateLicenseKey 熵不足（4 段 hex 仅 64 bit，B8 只修了兑换码未修 LicenseKey）；MAIL_FROM_ADDRESS 配置键层级错位永远不生效（恒回退 noreply@billing.com）；reissueLicense 注释称置 REISSUED 实际置 REVOKED；AdminController.reissueLicense 失败无审计（refundOrder 有，口径不一致）；JWS exp/iat 用系统时区（应 UTC）；License @Data + LAZY order 的 toString/equals 隐患；Aliyun/AWS KMS 构造期同步调云 API（与 Local 延迟加载哲学不一致）；AliyunKmsService 非 "EC" 一律按 RSA 静默处理；兑换码无过期批量清理任务；PENDING_ACTIVATION/SUSPENDED 死状态、activatedAt 从未赋值。

**基础设施**：无效配置键 `spring.api-docs.enabled`（正确为 springdoc 前缀）；pom 残留死属性、`jackson-datatype-jsr310`（Jackson2 模块，Boot4 已内置 java.time，且拖回 Jackson2 全栈）、`azure-security-keyvault-keys`（未实现未引用）三个无用依赖；README 偏差（V1-V6 应为 V1-V7、退款路径写错、payment.provider 配置项不存在）；.gitignore 首行被代码围栏污染；supportEmail 一处漏转义；evictStaleWindows 超阈值后每请求 O(n) 全表扫描；限流与发放锁均为单实例实现（水平扩容即击穿，部署文档需显著强调）。
