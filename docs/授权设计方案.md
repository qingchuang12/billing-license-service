# 授权 / License 设计方案

本文聚焦「非对称签名 License」这一子域：原理、算法、数据结构、格式、机器码、客户端离线验证、签发/换机/作废、密钥管理、版本控制、订阅、防破解。支付层与端到端业务流程见主文档。

---

## 一、授权模型总览

核心思路：

> **软件内置公钥；服务端 / 私钥端生成签名 License。**  
> **支付只负责卖“兑换码”或“订单凭证”。**  
> **用户付款后获得授权，软件验证签名后离线可用。**

三层结构：

| 层级 | 作用 | 是否需要联网 |
|---|---|---:|
| exe 客户端 | 试用、机器码、激活、校验 | 激活时可联网，之后可离线 |
| 授权服务 License Service | 生成签名 License | 发放 / 兑换时联网 |
| 支付平台 | 收钱、发货、订单 | 用户购买时联网 |

授权流程：

```text
1. 用户电脑生成机器码 machine_id
2. 用户付款
3. 授权服务根据机器码生成 License 数据
4. 用私钥对 License 数据签名
5. 用户得到 License 字符串或 License 文件
6. exe 内置公钥验证签名
7. 验证通过后解锁功能
```

关键点：**客户端没有私钥，所以用户无法自己伪造合法 License。**

---

## 二、签名算法选择

推荐优先级（与实际 KMS 抽象一致）：

| 算法 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| Ed25519（JWS `EdDSA`） | License 短、性能好、现代 | 部分环境需额外库 | 推荐新项目；纯本地文件 KMS 友好（本项目默认） |
| ECDSA P-256（JWS `ES256`） | 证书体系成熟、JDK 原生支持 | 签名稍长 | 纯本地文件 KMS 同样原生支持，无需云 KMS |
| RSA-2048 / RSA-3072（JWS `RS256`） | 多语言内置支持、兼容好 | License 字符串较长 | 推荐 C#/.NET 传统项目少依赖 |

实际实现：`LicenseIssuer#getJwsAlgorithm()` 按 KMS 返回算法映射 `EdDSA`/`ES256`/`RS256`，**算法通过 `kid` 标识**，无需在 payload 硬编码。

```bash
openssl genpkey -algorithm ed25519 -outform DER -out ed_private.der
openssl pkey -in ed_private.der -pubout -outform DER -out ed_public.der
tail -c 32 ed_private.der > private.key   # 裸 32 字节私钥
tail -c 32 ed_public.der  > public.key    # 裸 32 字节公钥
# 私钥挂 Secret/环境变量；公钥硬编码进客户端

```

## 三、License 数据结构设计

### 3.1 实际签名 payload（以代码为准）

`infrastructure/crypto/LicenseIssuer#issueLicense` 当前写入的字段（短键名）：

| 字段 | 含义 | 来源 |
|---|---|---|
| `lic` | License 唯一键 | `license.getLicenseKey()` |
| `cid` | 客户 ID | `license.getCustomerId()` |
| `sku` | 产品 SKU | `product.getSku()` |
| `plan` | 档位（Pro / Pro Plus / Subscription） | `product.getTier().name()` |
| `feat` | 权益清单 | `product.getFeatures()`（JSON 数组） |
| `mid` | 机器码（设备指纹） | `license.getMachineCode()`（兑换路径才有） |
| `oid` | 订单 ID | `license.getOrder().getId()` |
| `iat` | 签发时间（epoch 秒） | `ZonedDateTime.now()` |
| `exp` | 过期时间（epoch 秒，买断可为 null） | `license.getExpiresAt()` |
| `meta` | 扩展元数据 | `license.getMetadata()`（JSON 对象） |

### 3.2 文档原始建议字段（候选，未全部落地）

```json
{
  "license_id": "8f1c2a9e-4b7d-4a1e-9f2c-xxxxxx",
  "product_id": "your-tool-name",
  "plan": "pro",
  "type": "lifetime",
  "machine_id": "9f86d081884c7d65...",
  "issued_at": 1735689600,
  "expires_at": null,
  "update_until": 1767225600,
  "features": ["batch_process", "export_without_watermark", "advanced_settings"],
  "max_major_version": 1,
  "customer_email": "user@example.com",
  "order_id": "ORDER-20250101-0001"
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| license_id | 授权唯一 ID，方便售后 |
| product_id | 产品 ID，防止拿别的软件 License 来用 |
| plan | 套餐 free / pro / studio |
| type | lifetime / subscription / trial |
| machine_id | 设备指纹，绑定电脑 |
| issued_at | 发放时间 |
| expires_at | 过期时间，买断可为 null 或很大值 |
| update_until | 更新截止时间（已落地，A3） |
| max_major_version | 允许使用的最大版本（已落地，A3） |
| features | 功能权限列表 |
| order_id | 订单号，方便对账 |

> **已落地（2026-09-17，A3）**：`update_until` / `max_major_version` 已由 `LicenseIssuer#issueLicense` 写入 payload（见 §十 字段说明与 §三 示例）。Product 的 `updateUntilDays` / `maxMajorVersion` 为 null 或 ≤0 时对应键不出现，语义为「不限制」——**注意 `0` 不表示「不含更新」**，不要用 0 表达该语义。

## 四、License 格式

推荐使用 **JWS Compact Serialization（三段式）**，实际已实现：

```text
<base64url(header)>.<base64url(payload)>.<base64url(signature)>
```

Header 示例：

```json
{
  "alg": "ES256",
  "typ": "JWT",
  "kid": "license-key-1"
}
```

- `alg`：签名算法（`EdDSA` / `ES256` / `RS256`）。
- `typ`：固定 `JWT`（兼容 JWS 解析库）。
- `kid`：密钥标识，客户端按 `kid` 选择内置公钥，**支持密钥轮换**。

也可导出为 `license.lic` 文件：

```text
-----BEGIN YOURAPP LICENSE-----
<Base64Url(header)>.<Base64Url(payload)>.<Base64Url(signature)>
-----END YOURAPP LICENSE-----
```

软件应同时支持：① 输入激活码 / 兑换码；② 导入 `license.lic` 文件。

## 五、机器码设计

软件需生成稳定的机器码。

建议不要只用 MAC 地址（易变）。推荐组合：

```text
机器码 = SHA256(CPU ID + 磁盘序列号 + 主板序列号 + Windows 安装标识 + 固定盐)
```

显示格式化为 `XXXX-XXXX-XXXX-XXXX`（如 `A1B2-C3D4-E5F6-7890`）。

| 问题 | 建议 |
|---|---|
| 用户换硬件 | 提供换机 / 解绑机制 |
| 虚拟机环境 | 允许一定容错，或要求人工处理 |
| 磁盘更换 | 支持重新激活 |
| 重装系统 | 硬件不变则尽量保持机器码稳定 |
| 隐私 | 不上传完整硬件原始信息，只上传哈希 |

实际实现：服务端按字符串原样绑定校验（`licenses.machine_code`），客户端生成策略自定。

## 六、兑换流程（License 绑定设备）

用户拿到兑换码后在软件内输入：

```text
兑换码：XXXX-XXXX-XXXX-XXXX
```

软件请求授权服务（实际端点 `POST /api/redeem/redeem`）：

```json
{
  "code": "K7D2-9FQA-M3PZ-88BC",
  "customerEmail": "buyer@example.com",
  "machineId": "ABCD-1234-EFGH-5678"
}
```

授权服务返回（含签名 License）：

```json
{
  "success": true,
  "licenseKey": "XXXX-XXXX-XXXX-XXXX",
  "signedToken": "eyJhbGciOiJSUzI1...",
  "expiresAt": 1767225600
}
```

软件保存 License，后续离线使用。

> **一机一码要求**：只有兑换路径（`issueLicense(orderId, machineCode)`）会把 `mid` 写入 token；管理端批量签发路径当前未绑定 `mid`（见偏离清单），需补强以免“一码多机”。

## 七、客户端离线验证

软件启动 / 每次校验：

```text
1. 读取本地 License
2. 用内置公钥验证签名（必须验签，不能只查格式）
3. 校验 alg / kid 是否可信
4. 校验 product_id（实际为 sku）
5. 校验 machine_id（实际为 mid）== 当前设备
6. 校验 exp（未过期）
7. 校验 update_until / max_major_version（已落地，A3；键缺失即「不限制」）
8. 校验 features 是否含所需权益
9. 解锁功能
```

验证成功后**无需联网**。伪代码：

```text
function verifyLicense(licenseString):
    if licenseString is empty: return false
    parts = split(licenseString, ".")
    if parts.length != 3: return false

    sig = base64UrlDecode(parts[2])
    if not verifySignature(publicKey, parts[0] + "." + parts[1], sig):
        return false

    payload = jsonParse(base64UrlDecode(parts[1]))
    if payload.sku != PRODUCT_SKU: return false
    if payload.mid != currentMachineId(): return false
    if payload.exp != null and now() > payload.exp: return false
    if not featuresInclude(payload.feat, requiredFeature): return false
    return true
```

## 八、签发、换机与作废

### 8.1 签发

- 公开兑换路径：`issueLicense(orderId, machineCode)` —— 校验订单 `PAID` 后签名绑定设备。
- 管理端补偿：`POST /api/admin/orders/{orderNumber}/issue` —— Webhook 丢失时补发；当前路径**未绑定 `mid`**（待补强）。
- 私钥只在服务端 / KMS，客户端拿不到。

### 8.2 换机 / 重发（reissue）

```text
1. 用户输入邮箱 + 订单号 / License ID
2. 系统验证
3. 用户输入新机器码
4. 原 License 标记 REISSUED（非 REVOKED）
5. 签发新绑定新机器码的 License（reissuedFrom 指回原证）
```

风控：单 License 累计重发次数上限 + 同设备窗口内换机频控（`RateLimitService`）。

实际端点：`POST /api/admin/licenses/{licenseKey}/reissue?newMachineId=&reason=`。

### 8.3 作废 / 退款后失效（revoke）

实际端点：`POST /api/admin/licenses/{licenseKey}/revoke?reason=`（唯一吊销入口）。

离线 License 的难点：

> License 一旦发放到本地，即使后台作废，用户离线时仍可能继续使用。

应对：

- 买断制：后台标记 `REVOKED`；用户下次联网兑换 / 更新时失效，无法换机、无法更新、无法售后。
- 订阅制：必须定期联网校验（`exp` 到期即受限）。

## 九、密钥管理

### 9.1 私钥保护（最重要）

私钥绝对不能放在：exe 客户端、前端 JS、公开仓库、普通配置文件、员工个人电脑明文、日志、客服后台可下载位。

推荐优先级：`KMS/HSM > Secret Manager > 环境变量 > 配置文件`。

实际实现：`KmsService` 签名，私钥不出服务端；License 模块只访问 License 签名密钥，支付模块只访问支付密钥（权限隔离）。

### 9.2 密钥轮换（kid）

License 中带 `kid`（当前 `billing.license-kid`，默认 `license-key-1`）。推荐设计多个公钥：

```json
{
  "keys": [
    { "kid": "2025-01", "public_key": "..." },
    { "kid": "2026-01", "public_key": "..." }
  ]
}
```

软件内置多公钥，按 `kid` 选择；服务端 `verify` 按 `kid` 选对应公钥。买断 License 有效期长达数年，**轮换后旧证必须仍能验**，故 KMS 侧需密钥版本 / 别名支持。当前 `KmsService` 单密钥（所有 kid 映射到同一公钥），多密钥密码学轮换属基础设施层待补。

## 十、版本控制与更新门槛

买断制不要简单写“永久更新”。推荐：

```text
一次买断 = 永久使用当前大版本 + 一年小版本更新
```

License 中携带（已落地 A3，键名即实际签发键名）：

```json
{ "type": "lifetime", "update_until": 1767225600, "max_major_version": 1 }
```

> `update_until` = `iat + product.update_until_days × 86400`（秒）；`update_until_days` 为 null 或 0、
> `max_major_version` 为 null 时，对应键不出现在 payload 中，语义为「不限制」。

软件判断：

```text
if app_version <= max_major_version 且 now < update_until：
    正常更新
else：
    提示升级新版本需补差价
```

这样大版本升级可以收费。

## 十二、防破解建议

> Windows exe 没有绝对防破解方案，目标是**提高破解成本**。

1. **不要只用一个简单开关**：核心功能拆模块，授权判断分散到多个关键点，部分高级资源由 License 派生密钥解密。
2. **验证必须验签**：不能只检查字符串格式。
3. **公钥内置要谨慎**：公钥可被查看但没关系，只要私钥不泄露即无法伪造合法 License；需配合加壳 / 混淆 / 完整性检查防 patch exe、替换公钥。
4. **可加壳保护**：VMProtect / Themida / Enigma Protector（UPX 只是压缩，不作安全方案）。
5. **不要显示明确错误**：统一提示「激活失败，请检查激活码或联系支持」，避免暴露 `签名错误` / `机器码不匹配` 等定位信息。

## 十三、推荐落地清单（授权子域）

客户端要做：生成机器码、显示 / 复制机器码、试用控制、购买按钮、兑换码输入、License 导入、本地保存、公钥验签、校验 `mid` / `exp` / `feat`、激活状态页、换机提示。

授权服务要做：密钥对生成与 KMS 保管、生成 License、生成兑换码、兑换码绑定机器码、发放 License、查询 License、换机重发、作废 License、记录订单与事件、按 `kid` 验签、密钥轮换。

---

## 十四、一句话总结

> 用**非对称签名 License（JWS + KMS 私钥 + `kid` 轮换 + `mid` 设备绑定）**做离线授权；用户付款获得兑换码，软件联网兑换成绑定机器码的签名 License，之后离线可用；服务端保管私钥，支持换机重发与作废。

## 十五、服务端概要实现逻辑

> 以下逻辑以当前 Java 实现为准（`infrastructure/crypto/LicenseIssuer`、`service/LicenseService`、`infrastructure/kms/*`）。客户端集成以代码字段名为契约。

### 15.1 密钥与签名（`KmsService` + `LicenseIssuer`）

- 密钥加载：`LocalKmsService` 为唯一实现（纯本地文件方案，缺省即启用）。**延迟到首次 `sign/verify` 才读盘**，避免 k8s Secret / 配置中心挂载慢导致启动崩溃；路径优先级为环境变量 `PRIVATE_KEY_PATH`/`PUBLIC_KEY_PATH` → 回退 `application.yml` 的 `billing.private-key-path`/`public-key-path`（默认 `/keys/private.key`、`/keys/public.key`）。
- 算法：私钥文件格式必须与加载器匹配——Ed25519 为**裸 32 字节**（加载器手工包 DER 前缀）；EC / RSA 必须是 **PKCS#8 / X.509 的 DER 字节（非 PEM）**。`LicenseIssuer#getJwsAlgorithm()` 按 KMS 算法映射 JWS `alg`：`Ed25519→EdDSA`、`EC→ES256`、`RSA→RS256`。
- 签发（`LicenseIssuer.issueLicense`）：
  1. `header = {alg, typ:"JWT", kid}`（`kid` 取自 `billing.license-kid`，默认 `license-key-1`）；
  2. `payload = {lic, cid, sku, plan, feat, mid, oid, iat, exp, meta}`（`mid` 仅兑换路径有）；
  3. `signingInput = base64url(header)+"."+base64url(payload)`；
  4. `signature = kms.sign(signingInput.getBytes(UTF_8))`；
  5. 返回 `header.payload.signature` 三段式 token。
- 验签（`LicenseIssuer.verifyLicense`）：拆分三段 → 对 `parts[0]+"."+parts[1]` 用 `kms.verify(..., signature)` 验签（客户端离线强制点；服务端当前未在校验端点调用，见 §17.3）。

### 15.2 签发入口（`LicenseService`）

- 公开兑换 `issueLicense(orderId, machineCode)`：按 `orderNumber` 查订单 → 校验 `paymentStatus == PAID` → 取首个 product → 生成 `licenseKey`（UUID 段 `XXXX-XXXX-XXXX-XXXX`）→ `expiresAt = now + product.getLicenseDurationDays()` → 绑定 `machineCode` → 调 `LicenseIssuer` 签名 → 落库 → 记 `ISSUED` 事件。
- 管理端补偿 `issueLicensesForOrder`：按订单明细逐条 `createLicense`，**当前不绑 `mid`**（token 无 `mid`，客户端无法离线锁机，见偏离清单）。
- 支付成功 `fulfill`：订单带 `machine_id` 直接签发；否则只生成兑换码，等用户兑换。

### 15.3 换机与作废

- `reissueLicense`：原证置 `REISSUED`（非 `REVOKED`，换机与退款语义分离）→ 新证绑 `newMachineId` 且 `reissuedFrom` 指回原证 → 带风控（单证累计重发上限 + 同设备窗口限流 `RateLimitService`）。
- `revokeLicense`：置 `REVOKED` + `revokedAt`；离线 License 下次联网校验时失效。

### 15.4 校验端点

- `verifyLicense(key)`：查库 → 校验 `status == ACTIVE` 且未过期（过期自动置 `EXPIRED`）。
- ⚠️ 当前**未对 token 重新验签**（仅信库状态），纵深防御建议补 `licenseIssuer.verifyLicense()`（见 §17.3）。

## 十六、客户端概要实现逻辑（exe，通常 C#/.NET）

> 客户端仓库独立于本服务；以下为离线授权侧必须实现的逻辑，字段名以 §三 实际 payload 为准。

### 16.1 机器码与试用

- 机器码：`machineCode = SHA256(CPU ID + 磁盘序列号 + 主板序列号 + Windows 安装标识 + 固定盐)`，格式化展示 `XXXX-XXXX-XXXX-XXXX`；只上传哈希，不上传原始硬件信息。
- 试用：本地**加密**保存 `{first_run_at, trial_count, last_run_at, trial_token}`，绑定机器码 + 检测时间回拨；明文不存（只能提高破解成本）。

### 16.2 购买与兑换

- 购买：点击购买 → 打开收银台并自动带入 `machine_id` → 支付成功拿到兑换码。
- 兑换：`POST /api/redeem/redeem {code, customerEmail, machineId}` → 响应经**统一壳**包裹，业务字段在 `data` 段：
  `$.data = {success, licenseKey, signedToken, expiresAt, serverTime}`（`serverTime` 为 epoch 毫秒，客户端据此抬高本地时间下界，K4/2026-09-18）；也可「导入 `license.lic` 文件」。本地保存 `signedToken`。
  > ⚠️ **2026-09-18 更正**：本节此前写作扁平结构 `{success, licenseKey, signedToken, expiresAt}`，与运行时（`ApiResponseAdvice` 对所有端点统一包壳）不符——客户端曾据此实现，导致取不到 token、兑换必定失败（K1 已修）。

### 16.3 离线验签（核心，每次启动 / 功能解锁时）

```text
parts = token.split(".")
if parts.length != 3: 拒绝
sig = base64url解码(parts[2])
ok = Ed25519Verify(内置公钥[按 header.kid 选择], parts[0]+"."+parts[1], sig)
if not ok: 拒绝                         # 必须验签，不能只查格式
payload = 解码(parts[1])
if payload.sku not in 接受的SKU列表: 拒绝   # 服务端按档位（买断/订阅 × Pro/Pro Plus）使用不同 SKU
if payload.mid != 当前machineCode: 拒绝   # 一机一码
if payload.exp != null 且 now > exp: 拒绝
if 所需权益 not in (SKU映射权益 ∪ payload.feat): 拒绝   # 高级功能按权益控制
通过 → 解锁
```

> **权益口径（2026-09-18 对齐，K3）**：服务端 `feat` 取自 `products.features`，是**营销权益文案**
> （`OFFLINE` / `MULTI_DEVICE` / `EMAIL_SUPPORT` / …），与客户端的功能开关（`pro` / `cloud_sync`）不在同一层语义。
> 故客户端按 **SKU → 功能键** 映射解锁功能（`license.config.json` 的 `skuFeatures`），并把原始 `feat` 一并并入生效权益
> （服务端将来若直接下发功能键即自动生效）；接受的 SKU 列表由 `acceptedSkus` 配置（默认 = 服务端四个种子 SKU）。
> 两项均可由**包外配置**覆盖，服务端新增档位无需客户端发版。
> `update_until` / `max_major_version` 服务端已写入 payload，客户端仅解析、**尚未据此拦截**（属产品策略，待定）。

- 验证通过即**离线可用**，不再联网。
- 公钥编译期硬编码（多份以支持 `kid` 轮换）；错误统一提示「激活失败，请检查激活码或联系支持」，不暴露具体原因（防定位，见 §十二）。

### 16.4 换机与订阅

- 换机：联系后台 `reissue` 拿绑定新机码的新 License。
- 订阅（`exp` 存在）：每隔 3–7 天联网校验一次，过期进入只读 / 禁用高级功能 / 提示续费。

## 十七、免费生产的关键注意点

「免费」指无云 KMS 许可费——Ed25519 / EC / RSA 均靠 OpenSSL + JDK 原生生成，零成本。免费前提下**生产最佳为 Ed25519（JWS `EdDSA`）**：短 License、JDK 原生、与默认代码路径契合；私钥以本地文件挂载（k8s Secret / 环境变量），不进 Git。

1. **私钥安全**：Ed25519 私钥只挂 Secret / 环境变量，绝不进 Git / 前端 / 日志；公钥才硬编码进 exe。
2. **`kid` 轮换**：换密钥时保留旧公钥在客户端（按 `kid` 选），否则买断长周期旧证失验；当前 `KmsService` 单密钥，多公钥验证属基础设施待补。
3. **服务端补验签**：公开 `verify` 端点建议加 `licenseIssuer.verifyLicense()`，防止 token 被当凭证时篡改。
4. **管理端批量签发**：补 `mid` 绑定，否则该路径产出的 License 客户端无法离线锁机。

> 第 2–4 项在本文偏离清单已标「待补强」；若需集中管密钥且不引入云费用，可改用 HashiCorp Vault 开源版（免费）的 Transit 签名后端，新增一个本地 KMS 实现（如 Vault 后端）即可。
