## 一、业务梳理

### 1.1 定位与参与角色

统一「计费 + 许可证」服务，为桌面端 exe 工具提供 license 签发、兑换、换机与计费/退款后端。

| 角色 | 说明 | 交互方式 |
|---|---|---|
| exe 客户端 | 生成机器码、发起下单、轮询支付状态、兑换、离线验签 | 公开 HTTPS 端点 |
| 支付渠道 | 支付宝 / 微信支付（国内）；Stripe / Paddle / PayPal（国际） | 出站 SDK 调用 + 入站 Webhook |
| 运营/客服 | 订单查询、补签发、退款、License 作废/换机、兑换码管理 | 管理端 + 管理员 JWT |
| KMS | 签发私钥托管（local 文件，纯本地） | 进程内 `KmsService` 抽象 |
| SMTP | 支付成功/失败、退款、License 通知（`@Async`，未配置自动跳过） | 出站邮件 |
| PostgreSQL | 全部业务实体持久化（Flyway V1–V11 管 schema） | JPA |

### 1.2 业务域划分

| 业务域 | 端点前缀 | 鉴权 | 核心职责 |
|---|---|---|---|
| 收银台 | `/api/checkout/**` | 公开 | 下单唯一入口：区域定价、建单、建支付、查状态（含主动对账补偿） |
| 兑换码兑换 | `/api/redeem/redeem` | 公开 | 兑换码 → 绑定机器码的签名 License（含 IP 频控 + 暴力猜测拦截） |
| License 校验 | `/api/licenses/verify/{licenseKey}` | 公开 | 在线校验（离线验签的在线兜底） |
| 支付回调 | `/api/webhooks/{alipay,wechat,stripe,paddle,paypal}` | 公开（渠道自验签） | 验签 → 幂等 → 金额校验 → 发货 / 订阅生命周期 |
| 管理端 | `/api/admin/**` | 管理员 JWT（ROLE_ADMIN） | 订单查询/签发/退款、License 查询/作废/换机、兑换码生成/导出/撤销、渠道自查 |

### 1.3 收费模式与定价

- **三档**：Pro 买断 / Pro Plus 买断（一次性付费）/ 订阅制（Paddle、Stripe Billing 托管，自动续期与取消联动 License）。
- **双币种**：区域判定 `CheckoutService#isDomestic`（`currency=CNY` 或 `locale` 以 `zh` 开头 → 国内）。
  国内取 `Product.priceCny` + `CNY`，国际取 `Product.priceUsd` + `USD`；目标档位缺失**直接拒绝下单**（`PRICE_NOT_CONFIGURED`），禁止跨币种回退。
- **权益落地**：`Product.tier`（PRO / PRO_PLUS）与 `Product.features`（JSON 数组）写入 License payload 的 `plan` / `feat`。

### 1.4 状态机

| 对象 | 状态流转 | 唯一出口 |
|---|---|---|
| `Order.OrderStatus` | `PENDING` → `PAID` →（退款）`REFUNDED` / `REFUND_FAILED` | `markPaid()` / `markRefunded()` / `markRefundFailed()` |
| `Order.PaymentStatus` | `UNPAID` → `PAID` → `REFUNDED` | 同上（与 status 同步，避免双字段发散） |
| `CheckoutSession.Status` | `CREATED` → `PENDING` → `PAID` | `CheckoutService#markPaid` / 补偿路径 |
| `License.LicenseStatus` | `ACTIVE` → `EXPIRED` / `REVOKED`（退款）/ `REISSUED`（换机） | `reissueLicense` / `revokeLicense` |
| `RedeemCode.RedeemCodeStatus` | `UNUSED` → `USED` / `EXPIRED` / `REVOKED` | `doRedeem` / `revokeCode` |
| `Subscription.SubscriptionStatus` | `PENDING` → `ACTIVE` ⇄ `PAST_DUE` → `CANCELED` | `processSubscriptionEvent` |

### 1.5 关键业务规则（时序图中的分支依据）

1. **下单入口唯一**：仅 `POST /api/checkout/create`（原 `POST /api/orders` 已删除）。
2. **支付前不签发**：只有 Webhook 确认成功、或 `status` 主动对账确认成功后才发货。
3. **发货幂等（防资损）**：三层兜底 —— 订单状态机 `canFulfill()`、`PaymentEvent(provider,event_id)` 唯一约束原子预留、`getStatus`/`fulfillSession` 优先复用已签发的 License/兑换码（并按订单号加进程内锁）。
4. **渠道退款不成功绝不本地标成功**：`refundPayment` 返回 false 时，在 `REQUIRES_NEW` 独立事务中落 `REFUND_FAILED`（保留 `PAID`）并抛异常，交由人工到渠道控制台处理。
5. **Webhook 失败不吞**：验签失败 401、金额不符 400，**透传真实状态码**（微信侧仅 2xx 才返回 `{"code":"SUCCESS"}`），避免渠道误判投递成功而停止重试。
6. **风控**（`RateLimitService`，进程内滑动窗口）：邮箱购买频控、IP 兑换频控、兑换暴力猜测锁定、机器码换机频控、单 License 重发次数上限。
7. **响应壳**：除 Webhook（原样返回）与 springdoc 外，统一由 `ApiResponseAdvice` 包成 `{success,code,message,data,traceId,timestamp}`。

### 1.7 接口调用顺序（端到端总览）

> 本章给出**先调谁、后调谁**；各分支的失败路径与补偿细节见第三章，逐接口的**入参示例**见第四章。

#### 1.7.1 客户端购买主链路（两步下单 + 渠道回调）

```mermaid
sequenceDiagram
    autonumber
    participant C as "exe 客户端"
    participant S as "Billing & License 服务"
    participant CH as "支付渠道"
    participant M as "SMTP"

    C->>S: ① POST /api/checkout/create
    S-->>C: checkoutId + orderNumber + paymentMethods（当前区域可用渠道）
    C->>S: ② POST /api/checkout/{checkoutId}/select-provider  { provider }
    S->>CH: 创建支付会话（渠道 SDK / HTTP）
    CH-->>S: 渠道支付号 + 二维码 / 跳转链接
    S-->>C: paymentMode + qrcode / redirectUrl + expiresAt
    Note over C,CH: ③ 用户扫码或跳转完成付款（此步客户端不调用任何接口）
    CH->>S: ④ POST /api/webhooks/{alipay / wechat / stripe / paddle / paypal}
    Note over S: 验签 → 幂等预留 → 金额校验 → 发货（签发 License 或生成兑换码）
    S->>M: 支付成功通知邮件（@Async，未配置自动跳过）
    C->>S: ⑤ GET /api/checkout/{checkoutId}/status（轮询直至拿到凭证）
    S-->>C: license（signedToken）或 redeemCode
```

**调用次序**：`① create` → `② select-provider` → `③ 用户付款（无接口调用）` → `④ Webhook（渠道服务端发起）` → `⑤ status 取凭证`

**一步下单捷径**：`① create` 的请求体带 `provider` 时，服务端在同一事务内顺带完成第 ② 步，首次响应即含二维码 / 跳转链接 —— 次序简化为 `① → ③ → ④ → ⑤`（详见 §3.2）。

**为何 ⑤ 不可省**：第 ④ 步由渠道发起，公网回调可能丢失或验签失败；`⑤ status` 在查不到渠道已支付时会**主动向渠道对账并补发货**（详见 §3.3）。因此轮询既是取凭证，也是兜底，客户端只需稳定轮询。

#### 1.7.2 客户端兑换与校验链路

```mermaid
sequenceDiagram
    autonumber
    participant C as "exe 客户端"
    participant S as "Billing & License 服务"

    C->>S: ① POST /api/redeem/redeem  { code, customerEmail, machineId }
    Note over S: IP 频控 → 暴力猜测锁定 → 码状态校验 → 邮箱解析（未注册自动建访客账户）→ 签发 License
    S-->>C: licenseKey + signedToken + expiresAt
    Note over C: ② 本地离线验签（Ed25519，先读 JWS header 的 alg），不经过服务端
    C->>S: ③ GET /api/licenses/verify/{licenseKey}（仅离线验签失败时兜底）
    S-->>C: LicenseResponse（失效件返回 400）
```

**调用次序**：`① redeem` → `② 本地离线验签` →（仅失败时）`③ verify`

#### 1.7.3 客户端账号链路（v2.10 新增）

```mermaid
sequenceDiagram
    autonumber
    participant C as "exe 客户端"
    participant S as "Billing & License 服务"

    C->>S: ① POST /api/account/verification-code { email, purpose }
    Note over S: 三层限流（邮箱冷却/邮箱次数/IP 次数）→ 生成 6 位码 → 存 SHA-256(pepper+code) → 投递
    S-->>C: 200（data 为 null；联调模式从日志取码）
    C->>S: ② POST /api/account/register { email, password, emailCode }
    Note over S: 限流 → 邮箱唯一校验 → 密码策略 → 消费验证码 → 建号
    S-->>C: accessToken + expiresIn + user（注册成功即已登录）
    C->>S: ③ GET /api/account/me（Authorization: Bearer）
    Note over S: JwtAuthFilter：验签 → 过期 → 用户 ACTIVE → tokenVersion 一致
    S-->>C: user 资料
    C->>S: ④ POST /api/account/logout
    Note over S: tokenVersion + 1 → 该用户所有旧令牌立即失效
    S-->>C: 200（data 为 null）
    C->>S: ⑤ GET /api/account/me（带旧令牌）
    S-->>C: 401（令牌版本已失效）
```

**调用次序**：`① 发码` → `② 注册` → `③ me` → `④ 登出` → `⑤ me(401)`；已注册用户直接从 `POST /api/account/login` 进入 `③`。

**三个「必须知道」的约束**：

1. **发码与校验是两次请求**：验证码不在注册响应里返回；SMTP 未配置时服务端**静默跳过发送**，须开 `ACCOUNT_CODE_LOG_ONLY=true` 联调。
2. **登录失败锁定落库**：账号级计数在 `users.failed_login_count` / `locked_until`，跨重启有效；IP 级计数在内存（多实例部署会失效，与既有限制同源）。
3. **令牌失效靠 `tokenVersion`**：登出 / 改密 / 重置密码都只是 +1，`JwtAuthFilter` 每请求比对——因此「改密后旧设备仍在线」不会发生。

#### 1.7.4 管理端运维链路（全部需管理员 JWT：先以 `role=ADMIN` 的账号 `POST /api/account/login` 拿 `accessToken`，再带 `Authorization: Bearer <token>`）

| 场景 | 调用次序 | 关键说明 |
|---|---|---|
| 部署自检 | `GET /api/admin/payment-channels` | 先确认各渠道「配得对不对」，再跑真实交易；仅返回缺失配置项名，不回显密钥 |
| Webhook 丢失补发货 | `GET /api/admin/orders?orderNumber=` → `POST /api/admin/orders/{orderNumber}/issue` | 签发幂等，重复调用返回已签发记录（与自动发放同一服务方法） |
| 用户退款 | `GET /api/admin/orders?orderNumber=` → `POST /api/admin/orders/{orderNumber}/refund?reason=` | 渠道退款失败时落 `REFUND_FAILED`（保留 `PAID`）并抛异常，绝不谎报成功 |
| 售后换机 | `GET /api/admin/licenses?customerEmail=` → `POST /api/admin/licenses/{licenseKey}/reissue?newMachineId=` | 原证置 `REISSUED`，新证经 `reissuedFrom` 指回；受重发次数上限约束 |
| 违规作废 | `GET /api/admin/licenses/{licenseKey}` → `POST /api/admin/licenses/{licenseKey}/revoke?reason=` | 吊销唯一入口（客户端自吊销端点已删除） |
| 发卡给渠道方 | `POST /api/admin/redeem-codes/generate?productSku=&count=` → `GET /api/admin/redeem-codes?productSku=&status=` | 生成响应直接含码明文列表，便于导入发卡平台；事后可按产品/状态导出对账 |
| 兑换码作废 | `POST /api/admin/redeem-codes/revoke/{code}` | 已使用（`USED`）的码不可撤销 |

#### 1.7.5 用户端自助链路（U1/U2「我的授权」+ 自助退款）

| 场景 | 调用次序 | 关键说明 |
|---|---|---|
| 查看资产 | `GET /api/account/licenses` / `subscriptions` / `orders` | 仅本人资产；License 密钥**完整回显**（激活所需），离线验签 `signedToken` 不外发 |
| 退款入口显隐 | `GET /api/account/orders` | 服务端按 `RefundPolicy` 折算后回填 `refundable` / `refundableAmount`；**前端不做资格判断**，避免两处口径漂移 |
| 申请退款 | `POST /api/account/orders/{orderNumber}/refund` | 归属校验 → 限流 → 折算 → 复用 `AdminService.refundOrder(orderNumber, reason, 折算额)`；成功即吊销该订单全部 License |

**四条口径**（细节见 `README.md` §我的资产与自助退款）：

1. **越权按不存在返回**：非本人订单返回 `ORDER_NOT_FOUND`，不泄露他人订单存在性；越权请求不消耗限流配额。
2. **一单只退一次**：`paymentStatus ∈ {REFUNDED, PARTIALLY_REFUNDED}` 一律 `ALREADY_REFUNDED`。
3. **订阅订单不开放**：渠道侧无「取消订阅」调用能力，退款不取消订阅会持续扣款 → `NOT_REFUNDABLE` 引导人工。
4. **降级可追溯**：渠道不受理部分金额时自动改发全额退，并在订单 metadata 记 `refundDegraded`。

#### 1.7.6 凭证激活链路（plan-7.0 方案 A：单一入口）

> 此前客户端要认四条「绑定设备 + 拿签名令牌」的路径（购买直签 / 兑换码 / 在线校验 / 激活），
> 现收敛为**一个端点 + 一套返回**。该端点为**可选鉴权**（`JwtAuthFilter` 无令牌时不拦截，
> 仅跳过设置认证后放行），分支判定在服务端完成。

```mermaid
sequenceDiagram
    autonumber
    participant C as "exe 客户端"
    participant LC as "LicenseController"
    participant CBS as "CredentialBindingService"
    participant RCS as "RedeemCodeService"
    participant LS as "LicenseService 内核"

    C->>LC: POST /api/licenses/activate { credential, machineId, customerEmail? }
    Note over LC: 无条件用 ClientIpResolver 解析真实 IP 覆盖请求体<br/>（C10：禁止从请求体反序列化 IP，防伪造绕过限流）
    LC->>CBS: activate(request, currentUserIdOrNull())
    Note over CBS: 入参非空校验；按 credential 前缀分流

    alt credential 以 RC- 开头（兑换码）
        Note over CBS: 匿名可调（持码即持有人）；已登录时以登录账号邮箱覆盖请求体邮箱
        CBS->>RCS: redeemCode({ code, machineId, customerEmail, clientIp })
        Note over RCS: 整段复用既有频率控制与 B9 幂等<br/>（本层不重复计数，否则阈值被打对折）
        RCS-->>CBS: License
    else 其余（许可证密钥）
        Note over CBS: A5 安全红线：currentUserId == null → LOGIN_REQUIRED（不放行匿名绑定）
        CBS->>CBS: checkRedeemIp(clientIp)（全仓最严档 20/10min）
        CBS->>CBS: findByLicenseKey(credential).filter(customerId == currentUserId)
        Note over CBS: 越权与不存在同码返回 CREDENTIAL_NOT_FOUND，不泄露他人 License 存在性
        alt 已绑定同一机器
            Note over CBS: A3 幂等：直接返回既有 signedToken，绝不二次签发
        else 已绑定其他机器
            Note over CBS: MACHINE_MISMATCH（决策 B6：不自动改绑）<br/>恢复路径见 §3.14 账号页自助解绑
        else 未绑定
            CBS->>LS: bindToMachine(license, machineId, SRC_ACTIVATE)
            Note over LS: 先写 machineCode 再签名（顺序要紧，否则验签拿到旧绑定）<br/>→ save → MachineRegistryService.touch（C8 首次出现账本）
            CBS->>LS: recordLicenseEvent(license, ACTIVATED, machineId, ...)
        end
        Note over CBS: 任一 BusinessException → recordRedeemFailure(ip)<br/>达上限则以 REDEEM_BRUTE_FORCE 覆盖原错误（与兑换侧同口径）
    end

    CBS-->>LC: ActivateResponse
    LC-->>C: 200 { success, licenseKey, signedToken, status, machineId, expiresAt, serverTime }
    Note over C: 本地离线验签（Ed25519）；serverTime 抬高本地单调时间下界，防改系统时间复活过期授权
```

**调用次序**：`① activate（带 credential + machineId）` → `② 本地离线验签` →（仅失败时）`③ GET /api/licenses/verify/{licenseKey}`

**三条约束**：

1. **密钥分支改动不可放松**：账号页会明文展示 `licenseKey`，一旦置为匿名可绑，明文泄漏即等于「谁先抢到算谁的」——这是本设计不可松动的红线。
2. **兑换码分支不重写风控**：整段委托 `RedeemCodeService`，其内部已有 IP 频控 + 失败计数；本层再计一次会把阈值打对折。
3. **风控档位按最短板取严**：合并通道后密钥分支沿用兑换侧阈值（`redeemIpMax=20/10min`、`redeemFailureMax=10/10min`），因兑换码熵远低于许可证密钥、更易被暴力猜测。

## 二、横切机制时序

### 2.1 请求进入链：traceId → 鉴权 → 业务 → 响应壳

```mermaid
sequenceDiagram
    autonumber
    participant C as "调用方"
    participant TF as "TraceIdFilter"
    participant JF as "JwtAuthFilter"
    participant SC as "SecurityConfig"
    participant CT as "Controller"
    participant SV as "Service 层"
    participant ADV as "ApiResponseAdvice"
    participant GEH as "GlobalExceptionHandler"

    C->>TF: HTTP 请求
    Note over TF: @Order(-100)，复用入站 X-Trace-Id 或生成 16 位
    TF->>TF: MDC.put(traceId) + 响应头 X-Trace-Id
    TF->>JF: chain.doFilter
    Note over JF: 验签 Bearer JWT → 过期/ACTIVE/tokenVersion 校验 → 按 users.role 写 ROLE_USER 或 ROLE_ADMIN（A12 起管理端统一为管理员 JWT）
    JF->>SC: 授权判定
    alt /api/admin/**
        SC-->>C: 无 ROLE_ADMIN → 401 UNAUTHORIZED
    else /api/account/me、logout、password/change
        SC-->>C: 无 ROLE_USER → 401 UNAUTHORIZED
    else 公开端点 / permitAll
        SC->>CT: 放行
    else 其它路径
        SC-->>C: denyAll
    end
    CT->>SV: 业务调用（详见第三节）
    alt 正常返回
        SV-->>CT: DTO / Map
        CT->>ADV: beforeBodyWrite
        Note over ADV: 排除 String / byte[] / ApiResponse / .webhook. / .exception. / springdoc
        ADV-->>C: ApiResponse{success,code,message,data,traceId,timestamp}
    else 抛 BusinessException / ChannelDisabledException
        SV--)GEH: BusinessException(errorCode, message)
        GEH-->>C: 400 {success:false, errorCode, message, traceId}
    else 抛未知异常
        SV--)GEH: Exception
        GEH-->>C: 500 INTERNAL_ERROR（脱敏文案 + traceId，堆栈仅进服务端日志）
    end
    Note over TF: finally 输出 request audit 日志（method/uri/status/耗时/traceId）
```

**关注点**：
- traceId 存在**两套**：`TraceIdFilter` 写入 MDC 并回写响应头（正常路径）；`GlobalExceptionHandler#newTraceId()` **另生成**一个用于异常响应体。
  二者不一致 —— 异常响应体的 `traceId` 与响应头 `X-Trace-Id` 不同源，排查时以日志中的两个值交叉比对。
- `JwtAuthFilter` 只做认证不做授权；`/api/admin/**` 与需登录账号端点的 401 由 `SecurityConfig` 的 `HttpStatusEntryPoint` 产出。
- 启动期 fail-fast：鉴权无独立配置块（角色由 `users.role` 决定）；**`account.jwt-secret` 缺失或短于 32 字节则启动失败**（v2.10）；`payment.enabled-channels` 含无法识别渠道名则抛 `IllegalArgumentException`。
- 历史注记：`ApiKeyAuthFilter`（机读 `X-API-Key` 通道）与 `X-Admin-API-Key` 均已删除（A12 / 2026-09-23），管理端统一走管理员 JWT。

### 3.4 Webhook 支付回调 → 发货（主链路）

#### 3.4.1 渠道入口差异

| 端点 | 验签材料来源 |
|---|---|
| `POST /api/webhooks/alipay` | form-urlencoded body 中的 `sign`（`FormParamParser.parse`），**不在 Header** |
| `POST /api/webhooks/wechat` | Header `Wechatpay-Signature`（配合 Timestamp/Nonce/Serial）；成功才返回 `{"code":"SUCCESS","message":"OK"}` |
| `POST /api/webhooks/stripe` | Header `Stripe-Signature` |
| `POST /api/webhooks/paddle` | Header `Paddle-Signature` |
| `POST /api/webhooks/paypal` | Header `Paypal-Transmission-Id` |

#### 3.4.2 统一处理时序

```mermaid
sequenceDiagram
    autonumber
    participant CH as "支付渠道"

    WC->>PF: getStrategy(method)
    alt 渠道未启用
        PF-->>WC: ChannelDisabledException → 400
    end
    WC->>ST: verifyWebhookSignature(payload, signature, headers)
    alt 验签失败
        ST-->>WC: false
        WC->>PE: 不写入 payment_events（避免污染幂等表），仅 error 日志

    WC->>ST: parseWebhookPayload(payload)
    ST-->>WC: WebhookPayload{webhookEventId, transactionId, paymentId, orderId, amount, currency, status, subscriptionId, eventType, ...}

    WC->>PE: existsByProviderAndEventId(method.name(), eventId)
    alt 已处理
        WC-->>CH: 200 Already processed
    end

    alt 订阅事件（subscriptionId != null）
        WC->>WC: reserveEvent(...)（原子预留幂等行，唯一约束兜底并发）
        alt 预留失败（并发重复投递）

        end
        opt orderId 非空
            WC->>WC: self.fulfillOrder(orderId)
        end
        WC->>WC: subscriptionService.processSubscriptionEvent(...)  【见 3.5】
        WC-->>CH: 200 Success

        alt 金额/币种不符

            WC-->>CH: 400 Amount mismatch
        end
    end

    WC->>PS: updatePaymentStatus(paymentId, status, transactionId)
    PS->>DB: PaymentRepository.findByPaymentId → setStatus/setTransactionId/setPaidAt → save
    alt 支付记录不存在
        PS-->>WC: 抛异常 → warn 日志（不中断主流程）
    end

    alt status == SUCCESS
        WC->>WC: reserveEvent(...) 原子预留幂等行（发货前置）

        end

        WC->>DB: OrderRepository.findByOrderNumber(orderId)

                end
            end
        end
    else 非 SUCCESS（FAILED / PENDING 等）

    end
    WC-->>CH: 200 Success（微信侧返回 {"code":"SUCCESS"}）

    Note over C: 进入第二步：输入认证器动态码<br/>（或点「改用邮箱验证码」→ ㉟）
    C->>AMC: POST /api/account/mfa/verify {ticket, code}
    Note over AMC: permitAll + 方法内验票据（此端点须声明在 /api/account/** 规则之前，否则死锁）
    AMC->>MS: verify(ticket, code)
    MS->>MTS: parse(ticket)
    MTS-->>MS: userId + ver
    MS->>MS: 比对 ver == user.tokenVersion（改密即失效）<br/>校验账号状态 / 失败计数（verify-fail-max）
    MS->>TS: verify(解密后的 secret, code, lastUsedStep)
    Note over TS: 容错 ±1 步；已用过的 step 拒绝（防重放，RFC 6238 §5.2）
    alt 动态码未中且邮箱兜底开启
        MS->>MS: 校验 LOGIN_MFA 验证码（用途码只由本链路签发）
    end
    alt 通过
        MS->>MS: jwtTokenService.issue(userId, tokenVersion)
        MS-->>C: 200 {accessToken, expiresIn, user, mfaRequired=false}
    else 不通过
        MS-->>C: 400 MFA_CODE_INVALID / MFA_VERIFY_LIMIT / MFA_TICKET_INVALID
    end
```

> **票据密钥必须与 `account.jwt-secret` 隔离**：`JwtAuthFilter` 只看 `sub` + `ver` + 签名，若票据复用同一密钥，
> 票据本身就是一枚合法访问令牌——攻击者拿票据直接调 `/api/admin/**`，MFA 被整体绕过。此点由
> `MfaTicketServiceTest` 的机械断言锁住（票据不得通过 `JwtTokenService.parse`）。

### 4.4 支付回调（公开，由渠道服务端发起）

#### ⑥–⑩ `POST /api/webhooks/{alipay|wechat|stripe|paddle|paypal}`

入参为**各渠道原始报文**，不遵循统一请求体；签名位置随渠道而异：

| 端点 | 请求体 | 签名位置 |
|---|---|---|
| `/api/webhooks/alipay` | `application/x-www-form-urlencoded` 异步通知原文 | 表单参数 `sign` |
| `/api/webhooks/wechat` | 微信支付 v3 通知 JSON | 请求头 `Wechatpay-Signature` |

| `/api/webhooks/paddle` | Paddle 事件 JSON | 请求头 `Paddle-Signature` |
| `/api/webhooks/paypal` | PayPal 事件 JSON | 请求头 `Paypal-Transmission-Id` |

### 4.10 凭证激活与设备解绑（plan-7.0 方案 A）

> 激活是**公开端点但可选鉴权**（兑换码分支匿名可调、许可证密钥分支必须登录）；解绑在 `/api/account/**`（`ROLE_USER`）。
> 两者成对：激活在「已绑他机」时拒绝，解绑即为那条拒绝提示的恢复出口。

#### ㉝ `POST /api/licenses/activate` — 凭证激活（统一入口）

请求体（`dto/ActivateRequest`）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `credential` | string | ✅ | 兑换码（`RC-` 前缀）或许可证密钥；服务端按格式自动识别。空 → `CREDENTIAL_REQUIRED` |
| `machineId` | string | ✅ | 待绑定的客户端机器码。空 → `MACHINE_ID_REQUIRED` |
| `customerEmail` | string(email) | — | **仅兑换码分支且未登录时**需要（识别兑换人）；已登录时**以登录账号邮箱为准**，本字段被忽略 |

> `clientIp` **不在请求体中**（`@JsonIgnore` + `@Schema(hidden = true)`），由服务端按真实连接地址填充——防伪造 IP 绕过限流。

```bash
# ① 许可证密钥激活（须登录；未登录 → LOGIN_REQUIRED）
curl -X POST http://localhost:8000/api/licenses/activate \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <accessToken>" \
  -d '{"credential":"LIC-2F8A-7C31-9D04-B5E6","machineId":"ABCD-1234-EFGH-5678"}'

# ② 兑换码激活（匿名，与 ④ POST /api/redeem/redeem 等价）
curl -X POST http://localhost:8000/api/licenses/activate \
  -H "Content-Type: application/json" \
  -d '{"credential":"RC-8F3C-1D2E-9A4B","machineId":"ABCD-1234-EFGH-5678",
       "customerEmail":"buyer@example.com"}'
```

响应 `data`（`dto/ActivateResponse`，两条分支统一合同，口径对齐 `RedeemResponse`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `success` | boolean | 固定 `true`；与响应壳 `success` 同义，为兼容既有客户端保留 |
| `licenseKey` | string | License 密钥，客户端激活与在线校验用 |
| `signedToken` | string | 签名令牌（JWS Compact），供离线验签；请勿写入日志 |
| `status` | string | `ACTIVE` / `EXPIRED` / `REVOKED` / `REISSUED` |
| `machineId` | string | 本次绑定生效的机器码 |
| `expiresAt` | datetime / null | 过期时间；永久授权为 `null` |
| `serverTime` | number | 服务端当前时间（epoch 毫秒），防「改系统时间让过期授权复活」 |

**错误码**（按分支与语义类分组）：

| 语义类 | 兑换码分支 | 许可证密钥分支 |
|---|---|---|
| 入参缺失 | `CREDENTIAL_REQUIRED` / `MACHINE_ID_REQUIRED`（共用） | 同左 |
| **凭证不认识** | **`CREDENTIAL_NOT_FOUND`** | **`CREDENTIAL_NOT_FOUND`**（密钥不存在**或**非本人，同码返回不泄露存在性） |
| 凭证状态 | `CODE_ALREADY_USED` / `CODE_EXPIRED` | `LICENSE_NOT_ACTIVE` |
| 设备绑定 | — | `MACHINE_MISMATCH`（已绑他机，**不自动改绑** → 见 ㉞） |
| 身份 | `EMAIL_REQUIRED` / `INVALID_EMAIL`（未登录且未传邮箱 / 邮箱非法） | `LOGIN_REQUIRED` |
| 风控 | `REDEEM_IP_LIMIT` / `REDEEM_BRUTE_FORCE`（共用；档位沿用兑换侧：20 次/10 分钟、失败 10 次/10 分钟锁定） | 同左 |

> **B4（2026-09-23）：「凭证不认识」已统一为 `CREDENTIAL_NOT_FOUND`**。此前密钥分支返回 `LICENSE_NOT_FOUND`、
> 兑换分支返回 `CODE_NOT_FOUND`，客户端对接两个端点要认两个码。现由 `RedeemCodeService.doRedeem` 与
> `CredentialBindingService` 各出一处即完成统一——**不在激活层加「异常码翻译层」**，那本身是新漂移源。
> 本轮**只统一「凭证不认识」这一类**：`CODE_ALREADY_USED` / `CODE_EXPIRED` / `LICENSE_NOT_ACTIVE` 描述的是
> **凭证状态**而非识别失败，语义不同，保持原码。
>
> 另注：同为「密钥不存在」的 `GET /api/licenses/verify/{licenseKey}` 仍返回 `LICENSE_NOT_FOUND`（属第三个端点，
> 不在本次两端点范围）；管理端撤销兑换码 `revokeCode` 亦保留 `CODE_NOT_FOUND`。

> 幂等：已绑定**同一机器**时直接返回既有 `signedToken`，**不二次签发**。

#### ㉞ `POST /api/account/licenses/{licenseKey}/unbind` — 释放设备绑定（需登录）

无请求体。路径参数 `licenseKey` 必填。

```bash
curl -X POST http://localhost:8000/api/account/licenses/LIC-2F8A-7C31-9D04-B5E6/unbind \
  -H "Authorization: Bearer <accessToken>"
# → 200（data 为 null）
```

**错误码**：`LICENSE_NOT_FOUND`（密钥不存在**或**非本人，同码返回）、`LICENSE_REVOKED`（已吊销件无可解绑对象）。
本就未绑定时**幂等返回 200**（不落库、不重复留痕）。

> 与 ㉝ 的 `CREDENTIAL_NOT_FOUND` **刻意不同码**：本端点是「资产操作」（针对本人名下某个具体 License），
> 而 ㉝ 是「凭证识别」（一个可猜测的明文凭证能否换到绑定）。前者可由 `account.js` 按码映射文案
> 「许可证不存在或不属于当前账号」，后者刻意不区分「不存在/非本人」（防枚举）。

> 只清 `machineCode`（事件留痕 `UNBOUND`），**不吊销授权本身**；解绑后即可用 ㉝ 把该授权激活到新设备。

### 4.11 二次因子（MFA，plan-7.0 / B8）

> 前两个端点为**半认证**（`permitAll` + 方法内验票据）：调用者手里只有一枚「密码已通过」的一次性票据，
> 还没有访问令牌；后四个端点在 `/api/admin/**` 下，由框架统一要求 `ROLE_ADMIN`。

#### ㉟ `POST /api/account/mfa/challenge` — 发送邮箱兜底验证码（凭票据）

```json
{ "ticket": "eyJhbGciOiJIUzI1NiJ9..." }
```

```bash
curl -X POST http://localhost:8000/api/account/mfa/challenge \
  -H "Content-Type: application/json" -d '{"ticket":"eyJ..."}'
# → 200（data 为 null）
```

**错误码**：`MFA_TICKET_INVALID`、`MFA_NOT_ENABLED`、`MFA_EMAIL_FALLBACK_DISABLED`（服务端关闭了邮箱兜底）、
`CODE_SEND_TOO_FREQUENT`（沿用账号验证码的邮箱冷却与窗口阈值）。

#### ㊱ `POST /api/account/mfa/verify` — 校验第二因子并换取令牌（凭票据）

```json
{ "ticket": "eyJhbGciOiJIUzI1NiJ9...", "code": "123456" }
```

**响应**：与登录同构的 `AuthResponse`，**此处 `accessToken` 与 `user` 才非空**。

```bash
curl -X POST http://localhost:8000/api/account/mfa/verify \
  -H "Content-Type: application/json" -d '{"ticket":"eyJ...","code":"123456"}'
# → data: {"accessToken":"eyJ...","expiresIn":604800,"user":{...,"role":"ADMIN"},
#          "mfaRequired":false,"mfaTicket":null,"mfaMethods":null}
```

**错误码**：`MFA_TICKET_INVALID`（无效 / 过期 / `tokenVersion` 已变）、`MFA_NOT_ENABLED`、
`MFA_CODE_INVALID`（动态码与邮箱码**都不匹配**才算一次失败）、`MFA_VERIFY_LIMIT`（失败达 `verify-fail-max`）、
`MFA_SECRET_UNREADABLE`（密文损坏或 `ACCOUNT_MFA_KEY` 已轮换）、`ACCOUNT_DISABLED`。

#### ㊲ `GET /api/admin/mfa/status` — 查询绑定状态

无请求体、无路径参数。**响应不含任何密钥材料**。

```bash
curl http://localhost:8000/api/admin/mfa/status -H "Authorization: Bearer <admin-token>"
# → data: {"enabled":true,"enrolledAt":"2026-09-23T11:20:31","emailFallbackEnabled":true}
```

#### ㊳ `POST /api/admin/mfa/enroll` — 生成密钥（须当前密码）

```bash
curl -X POST http://localhost:8000/api/admin/mfa/enroll \
  -H "Authorization: Bearer <admin-token>" -H "Content-Type: application/json" \
  -d '{"password":"Passw0rd2026"}'
# → data: {"secret":"JBSWY3DPEHPK3PXP","otpauthUri":"otpauth://totp/...","activated":false}
```

**错误码**：`OLD_PASSWORD_MISMATCH`、`MFA_ALREADY_ENABLED`（重新绑定须先解绑）、`MFA_VERIFY_LIMIT`。

> `secret` / `otpauthUri` **仅此一次回显**，库中只存 AES-256-GCM 密文；故页面刷新即须重新生成。

#### ㊴ `POST /api/admin/mfa/activate` — 激活（认证器动态码）

```bash
curl -X POST http://localhost:8000/api/admin/mfa/activate \
  -H "Authorization: Bearer <admin-token>" -H "Content-Type: application/json" \
  -d '{"code":"123456"}'
# → 200（data 为 null）
```

**错误码**：`MFA_NOT_ENROLLED`（未先 enroll）、`MFA_CODE_INVALID`、`MFA_VERIFY_LIMIT`。

#### ㊵ `POST /api/admin/mfa/unbind` — 解绑（须密码 + 动态码/邮箱码）

```bash
curl -X POST http://localhost:8000/api/admin/mfa/unbind \
  -H "Authorization: Bearer <admin-token>" -H "Content-Type: application/json" \
  -d '{"password":"Passw0rd2026","code":"123456"}'
# → 200（data 为 null）
```

**错误码**：`MFA_NOT_ENABLED`、`OLD_PASSWORD_MISMATCH`、`MFA_CODE_INVALID`、`MFA_VERIFY_LIMIT`。

> **两道校验不可删**：只验密码则 session 被劫持后可静默关掉整道防线；只验动态码则密码泄漏即可关。
> 解绑**不**递增 `tokenVersion`（属保护等级下降，非账号异常）。

### 4.12 管理端 · License 处置（plan-7.0 主体三）

> 三者语义不同，售后须按实际情况择一。管理台「License 处置」分区即这三个动作的界面入口。

#### ㊶ `POST /api/admin/licenses/{licenseKey}/unbind` — 解绑设备（保留授权）

```bash
curl -X POST "http://localhost:8000/api/admin/licenses/{licenseKey}/unbind?reason=用户换机" \
  -H "Authorization: Bearer $ADMIN_TOKEN"
# → 200（data 为 null）
```

**错误码**：`LICENSE_NOT_FOUND`（密钥不存在，**做归属无关的精确匹配**）、`LICENSE_REVOKED`（已作废件无可解绑对象）。
本就未绑定时**幂等返回 200**（不落库、不重复留痕）。
留痕：`license_events` 记 `UNBOUND`，机器码取**解绑前**值，detail 形如 `Device binding released by admin. reason=…`。

> **与账号侧 ㉞ 的分工**：㉞ 要求「登录态 + 归属」（用户自助）；本端点供管理员处置——典型场景是
> 用户换机后旧令牌随旧机器失效、登不进账号页，客服只能代其释放绑定。故本端点**不做归属校验**，
> 把门交给 `/api/admin/**` 的 `ROLE_ADMIN` 框架授权。
> ⚠️ **本端点不吊销授权**——若需终止用户权益，用 `revoke`；若需换机并换新密钥，用 `reissue`。

#### `POST /api/admin/licenses/{licenseKey}/reissue` — 失效重发（参数已更新）

```bash
# 绑新机（常规）
curl -X POST "http://localhost:8000/api/admin/licenses/{licenseKey}/reissue?newMachineId=NEW-MACHINE&reason=changed_pc" \
  -H "Authorization: Bearer $ADMIN_TOKEN"
# 只失效重发、不绑设备（newMachineId 留空）
curl -X POST "http://localhost:8000/api/admin/licenses/{licenseKey}/reissue?reason=reset" \
  -H "Authorization: Bearer $ADMIN_TOKEN"
# 越过重发次数上限（客服人工处置；事件 detail 会标注 forced）
curl -X POST "http://localhost:8000/api/admin/licenses/{licenseKey}/reissue?force=true&reason=售后" \
  -H "Authorization: Bearer $ADMIN_TOKEN"
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `newMachineId` | 否 | **可留空**＝只失效重发、不绑设备（用户随后自行在新机激活） |
| `reason` | 否 | 重发原因，写入 `REISSUED` 事件 detail |
| `force` | 否 | 默认 `false`。为 `true` 时**越过** `billing.risk.license-reissue-max`（默认 5），越限时事件 detail 追加 `[forced over limit=N]` |

**错误码**：`LICENSE_NOT_FOUND`、`LICENSE_REVOKED`（**已作废件不可重发**——故「失效并重新生成 key」只能走本端点）、
`MACHINE_REISSUE_LIMIT`（同一机器码窗口内频繁换机）、`LICENSE_REISSUE_LIMIT`（**仅在 `force=false` 时**抛出）。

> 重发**不发邮件**；新证 `licenseKey` 随响应返回，同时会出现在该用户的账号页（`GET /api/account/licenses`
> 按 `customerId` 查、不过滤状态）。

### 4.13 凭证激活 · 自动上报绑定（plan-7.0 / D2）

#### ㊷ `POST /api/licenses/report-binding` — 客户端启动时上报机器码完成补绑

> **场景**：网购无机器码订单照常自动发兑换码（B2 = C）；客户在客户端激活时若**未携带机器码**，
> 该 License 落「未绑定」态。客户端在**程序启动时**把本机机器码上报一次，服务端据此补绑。
> **归属凭证 = `signedToken`（E1 = ①）**：签名令牌即授权本体，客户端在兑换 / 激活时**必然持有**
> （`LicenseService#bindToMachine` 对未绑定件也**无条件**签发），故本端点 **`permitAll`、无需登录**。

请求体（`dto/ReportBindingRequest`，`Content-Type: application/json`）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `signedToken` | string | 是 | 客户端持有的授权签名令牌（授权本体）；验签通过即证明归属 |
| `machineId` | string | 是 | 本机机器码（与激活同格式） |

```bash
curl -X POST http://localhost:8000/api/licenses/report-binding \
  -H "Content-Type: application/json" \
  -d '{"signedToken": "eyJhbGciOiJFZERTQSJ9...", "machineId": "ABCD-1234-EFGH-5678"}'
# → data 与 POST /api/licenses/activate 同构（ActivateResponse，含 signedToken / serverTime）
```

**行为**：验签通过 → 取 token 内 `lic` 载入授权 → 状态 `ACTIVE` 且**未绑定** → 补绑并**重签令牌**
（`bindToMachine` 先写机器码再签名，故响应中的 `signedToken` 已含本次机器码）、记事件 `BOUND_BY_REPORT`；
**已绑同机** → **幂等**返回既有状态（不二次签发）；**已绑他机** → `MACHINE_MISMATCH`
（守 B6 = A，不自动改绑，恢复路径为账号页 ㉞ / 管理端 ㊶ 解绑）。

**错误码**：`CREDENTIAL_REQUIRED` / `MACHINE_ID_REQUIRED`（入参非空）；验签失败 / 授权不存在 /
token 内无 `lic` **统一** `CREDENTIAL_NOT_FOUND`（B4 口径，不泄露 `licenseKey` 是否存在）；
`LICENSE_NOT_ACTIVE`（状态非 ACTIVE）；`MACHINE_MISMATCH`（已绑他机）；`REPORT_RATE_LIMIT`
（风控，按**机器码**维度限流，复用机器码限流档、独立命名空间 `machine-report`）。

> 留痕：`license_events` 记 `BOUND_BY_REPORT`，机器码登记来源 = `REPORT`。
> 与 ㉝（`POST /api/licenses/activate`）、㉞（账号侧解绑）同属凭证激活体系。

### 5.3 已识别的实现细节/不一致（供后续跟进）

1. **traceId 双源**：`TraceIdFilter`（MDC + 响应头）与 `GlobalExceptionHandler#newTraceId()`（异常响应体）各自生成，值不一致，异常场景无法用响应体的 traceId 直接检索到请求审计日志。
2. **进程内锁的部署边界**：`CheckoutService#fulfillmentLocks`、`RateLimitService#windows` 均为单实例内存态；多实例部署需要分布式锁与共享限流存储（代码注释已声明为已知限制）。
3. **`AdminService#resolveMethod` 为无用私有方法**：`refundOrder` 内未调用它（渠道解析走 `order.getPaymentProvider()` + `Payment.method` 回补），属可清理的死代码。
4. **`PaymentService#updatePaymentStatus` 在支付记录缺失时抛 `RuntimeException`**，会随 `processWebhook` 的 `@Transactional` 回滚整个 Webhook 处理（含已预留的幂等行），渠道重试时行为需关注。
5. **管理端作废丢失 `license_events` 留痕（plan-7.0 B11，2026-09-23 发现）**：活的作废路径 `AdminService#revokeLicense`（`:350-359`）只置 `REVOKED` + `revokedAt` 并 `log.info`，**不写 REVOKED 事件**；而带留痕的 `LicenseService#revokeLicense`（`:211-221`）**生产代码零调用**（仅 `LicenseServiceTest:157` 引用）——即作者把逻辑搬进 `AdminService` 时漏了留痕，原版沦为孤儿。后果：`license_events` 里永远查不到作废历史，售后只能靠 `@Audit` 审计日志反查。处置待定。
6. **解绑/重发两条路径的事件留痕口径**（对照项，非缺陷）：`LicenseService#unbindByAdmin` 与 `#unbindByOwner` **都**记 `UNBOUND` 事件；`reissueLicense` 记 `REISSUED`（旧证）+ `ISSUED`（新证）。故上条属作废单点遗漏，不是全链路通病。
