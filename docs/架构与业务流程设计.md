# 三、为什么推荐“合并成一个服务”？

对于独立 exe 工具，先不做微服务，采用**模块化单体 Modular Monolith**：

```text
billing-license-service
├── checkout / payments / orders / fulfillment
├── redeem / license / webhooks / admin / risk / notifier
```

优点：开发简单、部署简单、事务一致性好处理、回调/订单/授权逻辑易维护，后续再拆不晚。

---

# 四、核心设计原则

1. **支付和授权解耦**：支付层只负责收钱、确认成功、通知订单；授权层只负责生成/签名 License、绑定机器码、换机、作废。二者通过订单与事件连接。
2. **统一发货凭证**：无论国内/国外，统一发放 **Redeem Code 兑换码**，再换取 **Signed License**（统一所有渠道）。
3. **License 必须私钥签名**：客户端只内置公钥（专项见 授权设计方案.md）。
4. **支付成功页最好直接给 License**：若购买时已带 `machine_id`，支付成功直接显示 License 或「一键激活」；同时保留兑换码作为备份。

# 五、最佳用户流程

## 1. 客户端购买流程

```text
1. 用户打开 exe
2. 软件检测未激活
3. 软件生成机器码 machine_id
4. 用户点击购买
5. 软件自动复制机器码
6. 打开浏览器购买页（自动带入 machine_id）
7. 购买页识别地区/语言/币种
8. 用户选择支付方式并支付
9. 支付成功页显示 License / 兑换码
10. 用户回到软件激活
```

## 2. 国内用户流程

选择支付宝 / 微信 → 展示二维码或跳转收银台 → 支付成功后显示兑换码或直接显示 License，并发送邮件 / 订单查询入口。

## 3. 国外用户流程

选择 Paddle / Stripe / PayPal → 支付成功后显示 Redemption Code 或直接返回 License，发送 Receipt Email。

# 七、支付层设计

所有支付渠道实现同一接口（逻辑）：

```text
createCheckout(order)
verifyWebhook(request)
parsePaymentResult(payload)
refund(payment)
getPaymentStatus(providerId)
```

### 7.1 国内（支付宝 / 微信官方直连，已落地）

- **支付宝**：电脑网站支付或当面付二维码；RSA2 签名；校验 `notify_url` 回调签名、金额、商户订单号。
- **微信支付**：Native 支付；API v3 证书；回调验签 + 解密资源 + 校验金额 / 商户单号。
- 云闪付/银联、聚合支付：方案中列候选，**未实现**。

### 7.2 国外（Stripe / Paddle / PayPal，已落地）

- **Paddle**：海外软件销售主渠道，Merchant of Record，处理税务，Webhook 成熟。
- **Stripe**：信用卡 / Apple Pay / Google Pay，Stripe Checkout Session + `checkout.session.completed` Webhook。
- **PayPal**：PayPal Orders API + `PAYMENT.CAPTURE.COMPLETED` Webhook。

> 原始建议含 LemonSqueezy / Gumroad / 发卡平台，均未实现。

# 八、统一发货与兑换码

无论哪个渠道，支付成功后统一：

```text
当支付成功事件到达：
1. 查找订单
2. 校验订单状态
3. 若未发货：生成 Redeem Code
   - 若订单已有 machine_id：直接签发 License   # 见 授权设计方案.md
   - 否则：等待用户兑换
4. 更新订单为 fulfilled
5. 发送邮件
6. 记录事件
```

- **情况 A（带机器码）**：支付成功 → 直接签发绑定 `machine_id` 的 License → 成功页显示 → 一键激活（体验最好）。
- **情况 B（不带机器码）**：支付成功 → 生成兑换码 → 用户回软件输入 → 联网兑换 License → 激活（兼容性最好）。

# 九、Webhook 统一处理架构

```text
POST /api/webhooks/{provider}   # 实际为 /alipay / /wechat / /stripe / /paddle / /paypal
```

处理流程：

```text
1. 接收请求
2. 记录原始 payload
3. 验证签名
4. 提取 provider_event_id
5. 幂等判断
6. 标准化事件
7. 更新订单状态
8. 支付成功：创建兑换码 / 有 machine_id 则签发 License / 发邮件 / 记录审计
9. 返回 200
```

标准化支付事件（无论平台）：

```json
{
  "provider": "stripe",
  "event_id": "evt_123",
  "event_type": "payment_success",
  "order_id": "ord_20260101_0001",
  "provider_payment_id": "pi_123",
  "amount": 1499,
  "currency": "USD",
  "paid_at": 1735689600
}
```

Webhook 必须做的检查：签名验证、金额验证、币种验证、订单号验证、重复事件幂等、异常重试、失败报警。

# 十二、客户端激活设计

客户端界面建议：当前状态、机器码、[复制机器码]、[购买]、[输入兑换码]、[导入 License 文件]、[激活状态详情]。

一键激活可注册自定义协议：

```text
yourtool://redeem?code=K7D2-9FQA-M3PZ-88BC
```

> 更推荐传**兑换码**而非直接传 License（License 字符串可能很长，且浏览器可能拦截）；软件收到兑换码后自动联网兑换。

# 十三、订单 / 兑换码 / License 状态机

```text
Order:   PENDING → CONFIRMED → PROCESSING → COMPLETED / CANCELLED / REFUNDED / REFUND_FAILED / PAID
Redeem:  unused → used （异常：revoked / expired）
License: active → reissued / revoked / expired
```

退款：订单标记 `REFUNDED` → License 标记 `REVOKED`（离线 License 下次联网校验时失效，详见 授权设计方案.md）。

---

# 十四、退款处理方案

- **国内**（支付宝 / 微信）：商户后台主动发起退款接口 → 同步/回调 → 订单 `REFUNDED` → License `REVOKED` → 禁止换机/更新/售后。
- **国外**（Paddle / Stripe / PayPal）：平台退款 Webhook → 订单 `REFUNDED` → License `REVOKED`。
- **离线 License 限制**：无法立即失效，但可禁止换机/重新下载/更新/云服务/售后，下次联网校验失效；订阅制须定期联网校验（见 授权设计方案.md）。

# 十五、试用与风控设计

## 试用策略

推荐「次数试用 + 高级功能限制」（如免费 10 次 / 7 天 / 基础免费+高级付费）。本地试用记录**加密存储、绑定机器码、记录 last_seen 防回拨**，不要明文存 `trial_count`。

## 风控点

同一邮箱大量购买、同一机器码频繁换机、同一 IP 高频兑换、兑换码暴力猜测、异常退款率、License 被大量重复使用。建议：兑换码接口限流、机器码异常告警、License 重发次数限制、管理后台人工审核。（实际限流为进程内 `RateLimitService`。）

# 十六、密钥与安全管理

## 支付密钥（隔离）

支付宝应用私钥、微信 API 证书、Stripe Secret Key、PayPal Client Secret、Paddle API Key —— 均放 Secret Manager。支付模块只访问支付密钥。

## License 签名私钥

> 见 [`授权设计方案.md`](./授权设计方案.md) §九：KMS/HSM 保管、权限隔离、按 `kid` 轮换、多公钥验证。

推荐权限隔离：支付模块只能访问支付密钥；License 模块只能访问 License 签名密钥；管理后台不能导出私钥；签名通过 KMS API 完成。

## 2. 支付成功 Webhook

```text
POST /api/webhooks/{provider}
if not verifySignature(request): return 200
event = parseEvent(request.body)
if eventAlreadyProcessed(event.id): return 200
normalized = normalizePaymentEvent(event)
order = findOrder(normalized.order_id)
if order.paymentStatus != PAID:
    if normalized.amount != order.amount: markRiskAlert(); return 200

```

## 3. 发货逻辑

```text
function fulfill(order):
    redeemCode = createRedeemCode(order.id)
    if order.machine_id != null:
        license = issueLicense({ order_id, product_id, machine_id, plan })  # 见 授权设计方案.md
    sendEmail(order.email, redeemCode, license)
    order.status = "fulfilled"; save(order)
```

## 4. 兑换 License

```text
POST /api/redeem/redeem
redeemCode = findRedeemCode(body.code)
if redeemCode.status != "unused": return error
order = findOrder(redeemCode.order_id)
license = issueLicense({ order_id, product_id, machine_id: body.machineId, plan })
redeemCode.status = "used"; redeemCode.used_machine_id = body.machineId; save
return { license: license.signedToken }
```

## 5. License 签发

```text
function issueLicense(params):
    payload = { lic, cid, sku, plan, feat, mid, oid, iat, exp, meta }   # 实际字段见 授权设计方案.md
    signature = kms.sign(base64url(header) + "." + base64url(payload))
    token = header + "." + payload + "." + signature
    saveLicense(payload, token)
    return token
```

# 二十一、一句话最终方案

> **做一个统一的 Billing & License Service。** 国内通过支付宝 / 微信官方直连，国外接入 Paddle / Stripe / PayPal。所有支付成功后统一生成兑换码；若购买时带机器码则直接签发绑定设备的非对称签名 License（专项见 [`授权设计方案.md`](./授权设计方案.md)）。客户端内置公钥验证 License，激活后离线可用。服务端用 KMS/HSM 保管私钥，Webhook 统一验签、幂等、对账和发货。
