下面给你一套**授权服务 + 支付层合并架构**的完整设计方案，按“最佳实践、可落地、适合 exe 独立工具软件”的方式整理。

目标是：

> **国内支持支付宝、微信、云闪付。**  
> **国外支持 Paddle、Stripe、PayPal 三个主流平台。**  
> **统一订单、统一兑换码、统一非对称签名 License。**  
> **用户支付后自动获得授权，软件可离线验证。**  
> **服务端采用“支付授权一体化服务”，但模块隔离，方便后期拆分。**

---

# 一、最终推荐方案结论

我建议采用：

```text
模块化单体服务：Billing + License Service
统一收银台 Checkout
统一订单 Order
统一兑换码 Redeem Code
统一 License Issuer
KMS/HSM 管理签名私钥
Webhook 统一回调处理
支付成功后自动发货
```

## 推荐支付组合

### 国内

推荐：

```text
持牌聚合支付服务商
一次性支持：
- 支付宝
- 微信支付
- 云闪付/银联
```

原因：

- 不用分别对接三套支付接口；
- 回调格式统一；
- 对账更简单；
- 适合快速上线；
- 可后续切换为官方直连。

如果你有企业资质，并且希望长期正规运营，也可以选择：

```text
支付宝官方直连
微信支付官方直连
银联/云闪付官方直连
```

但开发成本和对账成本更高。

---

### 国外

推荐三个主流平台：

```text
Paddle
Stripe
PayPal
```

原因：

| 平台 | 作用 |
|---|---|
| Paddle | 面向软件销售，Merchant of Record，可处理海外税务 |
| Stripe | 主流信用卡、Apple Pay、Google Pay，体验好 |
| PayPal | 海外用户覆盖面广，作为补充钱包 |

如果你想更偏向独立开发者，也可以把：

```text
Paddle 替换成 LemonSqueezy
```

架构完全一样。

# 三、为什么推荐“合并成一个服务”？

对于独立 exe 工具，不建议一开始把支付服务和授权服务拆成多个微服务。

推荐：

```text
模块化单体 Modular Monolith
```

也就是一个后端项目，但内部模块清晰：

```text
billing-license-service
├── checkout
├── payments
├── orders
├── fulfillment
├── redeem
├── license
├── webhooks
├── admin
├── risk
└── notifier
```

优点：

- 开发简单；
- 部署简单；
- 事务一致性好处理；
- 回调、订单、授权逻辑容易维护；
- 后续业务增长后再拆分也不晚。

# 四、核心设计原则

## 1. 支付和授权解耦

支付层只负责：

```text
收钱
确认支付成功
通知订单系统
```

授权层只负责：

```text
生成 License
签名 License
绑定机器码
换机
作废授权
```

二者通过订单和事件连接。

---

## 2. 统一发货凭证

无论国内还是国外支付，统一发放：

```text
Redeem Code 兑换码
```

然后由兑换码换取：

```text
Signed License
```

这样可以统一所有渠道。

---

## 3. License 必须私钥签名

客户端只内置公钥。

```text
私钥：服务端/KMS
公钥：exe 内置
```

License 由服务端签名，客户端不能生成合法授权。

---

## 4. 支付成功页最好直接给 License

如果用户购买时已经带上了机器码：

```text
软件打开购买页时自动传入 machine_id
```

那么支付成功后可以直接显示：

```text
License 字符串
```

或提供：

```text
一键激活按钮
```

同时也保留：

```text
兑换码
```

作为备份。

# 七、支付层设计

## 支付层统一抽象

所有支付渠道都实现同一个接口：

```text
PaymentProvider Interface
```

逻辑上类似：

```text
createCheckout(order)
verifyWebhook(request)
parsePaymentResult(payload)
refund(payment)
getPaymentStatus(providerId)
```

---

## 1. 国内支付适配器

如果你使用聚合支付：

```text
DomesticAggregateProvider
```

它内部封装：

```text
支付宝
微信
云闪付
```

对上层只暴露统一接口。

如果你选择官方直连，则分为：

```text
AlipayProvider
WeChatPayProvider
UnionPayProvider
```

---

### 支付宝

推荐方式：

```text
电脑网站支付
或
当面付二维码
```

关键点：

- 签名方式：RSA2；
- 回调地址：`notify_url`；
- 同步返回：`return_url`；
- 必须校验回调签名；
- 必须校验订单金额；
- 必须校验商户订单号。

---

### 微信支付

推荐方式：

```text
Native 支付
```

用户扫码。

关键点：

- 使用商户号；
- API v3 证书；
- 回调验签；
- 解密回调资源；
- 校验金额；
- 校验商户单号。

---

### 云闪付/银联

推荐方式：

```text
银联在线支付
或
银联二维码
或
聚合支付中的云闪付通道
```

关键点：

- 银联证书较多，直连复杂；
- 建议优先通过聚合支付接入；
- 回调验签严格；
- 对账要注意币种和商户号。

---

## 2. 国外支付适配器

### Paddle

推荐用途：

```text
海外软件销售主渠道
```

优点：

- Merchant of Record；
- 处理海外税务；
- 适合卖软件 License；
- 支持订阅和一次买断；
- Webhook 成熟。

接入方式：

```text
Paddle Checkout
Webhook 通知
```

---

### Stripe

推荐用途：

```text
信用卡、Apple Pay、Google Pay
```

优点：

- 支付体验好；
- 开发者生态成熟；
- 支持 Stripe Checkout；
- 支持 Webhook；
- 可配合 Stripe Tax 处理税务。

接入方式：

```text
Stripe Checkout Session
Webhook checkout.session.completed
```

---

### PayPal

推荐用途：

```text
PayPal 钱包用户
```

优点：

- 海外用户覆盖广；
- 部分用户习惯 PayPal；
- 提高转化率。

接入方式：

```text
PayPal Orders API
Webhook PAYMENT.CAPTURE.COMPLETED
```

# 八、授权服务设计

授权服务负责生成和验证 License。

---

## 1. License Issuer

核心职责：

```text
生成 License Payload
使用私钥签名
返回 License 字符串
记录 License
支持换机重发
支持作废
```

---

## 2. 签名算法推荐

优先级：

```text
1. Ed25519
2. ECDSA P-256
3. RSA-2048 / RSA-3048
```

推荐：

| 场景 | 推荐算法 |
|---|---|
| 新项目、希望 License 短 | Ed25519 |
| 使用云 KMS | ECDSA P-256 |
| C#/.NET 想少依赖 | RSA-2048 |

如果你使用云厂商 KMS，通常：

```text
ECDSA P-256 更容易支持
```

因此一个稳妥组合是：

```text
License 签名算法：ECDSA P-256 / ES256
License 格式：JWT / JWS Compact
```

---

## 3. License 格式推荐

推荐使用：

```text
JWS Compact Serialization
```

例如：

```text
eyJhbGciOiJFUzI1NiIsImtpZCI6IjIwMjYtMDEifQ
.
eyJqdGkiOiJsaWNfMTIzIiwicHJvZHVjdCI6InRvb2wifQ
.
MEUCIQDx...
```

Header：

```json
{
  "alg": "ES256",
  "kid": "2026-01"
}
```

Payload：

```json
{
  "jti": "lic_8f1c2a9e",
  "product": "your-tool-name",
  "plan": "pro",
  "type": "lifetime",
  "machine_id": "ABCD-1234-EFGH-5678",
  "iat": 1735689600,
  "exp": null,
  "update_until": 1767225600,
  "max_major_version": 1,
  "features": [
    "batch_process",
    "export_no_watermark",
    "advanced_settings"
  ],
  "order_id": "ord_20260101_0001"
}
```

客户端验证：

```text
1. 校验 alg 是否符合预期
2. 校验 kid 是否可信
3. 使用内置公钥验签
4. 校验 product
5. 校验 machine_id
6. 校验 exp / update_until
7. 校验 features
```

# 十一、核心 API 设计

---

## 1. 创建收银台

客户端打开网页前，也可以由网页前端创建。

```http
POST /api/checkout/create
```

请求：

```json
{
  "product_id": "yourtool_pro",
  "currency": "CNY",
  "locale": "zh-CN",
  "machine_id": "ABCD-1234-EFGH-5678",
  "email": "optional@example.com",
  "return_url": "https://pay.yourapp.com/success",
  "cancel_url": "https://pay.yourapp.com/cancel"
}
```

响应：

```json
{
  "checkout_id": "chk_01JXYZ",
  "payment_methods": [
    "alipay",
    "wechat_pay",
    "unionpay"
  ],
  "pay_url": "https://pay.yourapp.com/checkout/chk_01JXYZ"
}
```

---

## 2. 选择支付方式

```http
POST /api/checkout/{checkout_id}/select-provider
```

请求：

```json
{
  "provider": "wechat_pay"
}
```

响应：

```json
{
  "provider": "wechat_pay",
  "payment_mode": "qrcode",
  "qrcode": "weixin://wxpay/bizpayurl?pr=xxxx",
  "expires_at": 1735693200
}
```

国外支付可能返回跳转地址：

```json
{
  "provider": "stripe",
  "payment_mode": "redirect",
  "redirect_url": "https://checkout.stripe.com/..."
}
```

---

## 3. 查询支付状态

前端轮询：

```http
GET /api/checkout/{checkout_id}/status
```

响应：

```json
{
  "status": "paid",
  "order_id": "ord_20260101_0001",
  "license": "eyJhbGciOiJFUzI1...",

```

如果没有，则只返回兑换码。

```text
}
```

---

## 2. 支付成功 Webhook

```text
POST /api/webhooks/stripe

if not verifyStripeSignature(request):
    return 200

event = parseStripeEvent(request.body)

if eventAlreadyProcessed(event.id):
    return 200

normalized = normalizePaymentEvent(event)

order = findOrder(normalized.order_id)

if order.status != "pending_payment":
    return 200

if normalized.amount != order.amount:
    markRiskAlert()
    return 200

order.status = "paid"
save(order)

fulfill(order)
```

---

## 3. 发货逻辑

```text
function fulfill(order):

    redeemCode = createRedeemCode(order.id)

    if order.machine_id != null:
        license = issueLicense({
            order_id: order.id,
            product_id: order.product_id,
            machine_id: order.machine_id,
            plan: order.plan
        })
    else:
        license = null

    sendEmail(order.email, redeemCode, license)

    order.status = "fulfilled"
    save(order)
```

---

## 4. 兑换 License

```text
POST /api/redeem

redeemCode = findRedeemCode(body.redeem_code)

if redeemCode.status != "unused":
    return error

order = findOrder(redeemCode.order_id)

if order.status != "paid" and order.status != "fulfilled":
    return error

license = issueLicense({
    order_id: order.id,
    product_id: order.product_id,
    machine_id: body.machine_id,
    plan: order.plan
})

redeemCode.status = "used"
redeemCode.used_machine_id = body.machine_id
save(redeemCode)

return {
    license: license.token
}
```

---

## 5. License 签发

```text
function issueLicense(params):

    payload = {
        jti: uuid(),
        product: params.product_id,
        plan: params.plan,
        type: "lifetime",
        machine_id: params.machine_id,
        iat: now(),
        update_until: now() + 365 days,
        max_major_version: 1,
        features: [
            "batch_process",
            "export_no_watermark"
        ],
        order_id: params.order_id
    }

    signature = kms.sign(payload)

    token = base64url(header) + "." + base64url(payload) + "." + base64url(signature)

    saveLicense(payload, token)

    return token
```

# 二十六、一句话最终方案

你要的“授权服务和支付层合并架构”最佳方案是：

> **做一个统一的 Billing & License Service。**  
> **国内通过持牌聚合支付接入支付宝、微信、云闪付；国外接入 Paddle、Stripe、PayPal。**  
> **所有支付成功后统一生成兑换码；如果购买时带有机器码，则直接签发绑定设备的非对称签名 License。**  
> **客户端内置公钥验证 License，激活后离线可用。**  
> **服务端用 KMS/HSM 保管私钥，Webhook 统一验签、幂等、对账和发货。**

这套架构既能快速上线，也足够支撑后续订阅、换机、退款、风控和多产品授权。
